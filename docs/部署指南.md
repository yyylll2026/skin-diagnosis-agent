# 部署指南

本项目的部署难点不在于「跑一个 FastAPI」，而在于**它要在本地跑两个模型**：

| 模型 | 用途 | 体积 |
|------|------|------|
| `qwen2.5vl:7b` / `qwen2.5vl:3b` | 图像识别（多模态） | 6.0 GB / 3.2 GB |
| `bge-m3` | 知识库向量化 | 1.2 GB |

因此筛选部署方案的**硬门槛**是：

1. 内存 ≥ 8 GB（7B 量化）或 ≥ 4 GB（3B）
2. 磁盘 ≥ 10 GB 放模型
3. **允许常驻进程 + 支持 SSE 长连接**
4. 最好有 GPU，否则单张图推理要几十秒到几分钟

第 3 条直接淘汰了 Vercel / Netlify Functions / Render 免费档这类 Serverless 平台。

---

## 一、免费方案对照

| 平台 | 免费规格 | 可行性 | 关键限制 |
|------|---------|--------|---------|
| **魔搭创空间** | 2 核 / 16 GB，Docker 类型 | ✅ **推荐** | 需阿里云实名认证；端口固定 7860；CPU 推理慢 |
| HuggingFace Spaces | 2 核 / 16 GB / 50 GB | ⚠️ 国内访问受限 | 48 小时无访问休眠；磁盘临时，重启要重下模型；免费 GPU 每天仅 3.5 分钟 |
| Oracle Cloud 永久免费 | ARM 4 核 / 24 GB | ✅ 真 VPS | 注册门槛高（信用卡验证）；ARM 容量常年售罄 |
| Google Colab / Kaggle | T4 / 16 GB 显存 | ⚠️ 仅演示 | 会话约 12 小时断连；无固定公网地址；不能当服务器 |
| Render / Railway / Fly.io 免费档 | 512 MB | ❌ | 内存差约 20 倍；不支持长连接流式 |
| 云厂商学生机 | 2 核 / 2~4 GB | ❌ | 内存装不下 7B 量化模型 |
| Vercel / CF Pages / Netlify | 不限带宽静态托管 | ✅ 仅前端 | 跑不了后端与模型 |

**结论：对国内用户，「免费 + 国内直连 + 能跑模型」三者只能同时满足于魔搭创空间。**

## 二、方案 A：魔搭创空间（推荐）

完整的逐步操作见 **[`../deploy/README.md`](../deploy/README.md)**。这里只说明架构上的适配点。

### 交付物

```
项目根目录/
├── Dockerfile          # 单容器：Ollama + FastAPI + 前端静态资源
├── ms_deploy.json      # 创空间配置：sdk_type=docker, port=7860
├── deploy/entrypoint.sh
└── .dockerignore / .gitattributes
```

### 四个必须做的适配

**1. 前后端合并进一个容器。**
平台只转发单一入口端口，前端与 API 必须由同一个服务提供。
本项目让 **FastAPI 同源托管前端构建产物**（`app/main.py` 的 `resolved_web_dir` 逻辑），
而不是引入 Nginx——少一个进程，在只有 2 核的机器上这很实际。
同源还有个附带好处：**前端用相对路径 `/api/v1/...` 天然指向同一后端，CORS 与代理配置全部免除**。

> 注意路由注册顺序：`StaticFiles` 挂载在 `/`，必须放在所有 API 路由**之后**，
> 否则会吞掉后续注册的路由（这个坑已踩过并有回归测试锁住）。

**2. 容器内要跑两个进程。**
`deploy/entrypoint.sh` 负责编排：后台起 `ollama serve`（只监听 127.0.0.1），
前台起 `uvicorn`（监听 0.0.0.0:7860）。用 `trap` 转发退出信号，避免容器停止时留下僵尸进程。

**3. 启动顺序：先起 API，再后台拉模型。**
如果反过来，首次部署时端口要等 4 GB 模型下完才可用，用户看到的是空白页。
先起 API 的话前端立刻能打开，健康面板如实显示「向量模型未就绪」，
模型到位后自动转正常。这正是把 `/system/health` 设计成**诊断面板**而不是**存活探针**的意义。

**4. 模型与数据必须落到持久化目录。**
容器默认文件系统重启即清空。镜像里写死了两处重定向：

```dockerfile
ENV OLLAMA_MODELS=/mnt/workspace/ollama-models   # 模型（4.4 GB）不再重下
ENV SKIN_DATA_ROOT=/mnt/workspace/data           # 向量库/会话/上传文件
```

`SKIN_DATA_ROOT` 是本项目为此新增的配置项，它统一重定位
向量库、SQLite、上传目录与日志，本地开发时留空即可回落到 `backend/data`。

### 环境变量

在创空间设置里覆盖，无需重新构建镜像。详见 [`../deploy/README.md`](../deploy/README.md#四可调环境变量)。

## 三、方案 B：任意 VPS / 支持多容器的平台

如果有真正的服务器（Oracle 永久免费 ARM、付费云主机、家里的小主机都行），
直接用仓库根目录的 `docker-compose.yml`，它是为「多容器 + GPU 直通」设计的：

```bash
docker compose up -d --build
# 前端 http://<服务器IP>:8080 ｜ 后端 http://<服务器IP>:8000/docs
```

默认假设 Ollama 跑在宿主机（这样才能直接用到 GPU）；
也可以启用 compose 文件里注释的 `ollama` 服务把模型也容器化（Linux + NVIDIA 需要
`nvidia-container-toolkit`）。

**手动部署（不用 Docker）**：

```bash
# 1. 装 Ollama 并拉模型
curl -fsSL https://ollama.com/install.sh | sh
ollama pull qwen2.5vl:7b && ollama pull bge-m3

# 2. 后端
cd backend && python -m venv .venv && .venv/bin/pip install -e ".[dev]"
cp .env.example .env
.venv/bin/python -m scripts.ingest_cli ingest ./data/docs -c 皮肤疾病
.venv/bin/uvicorn app.main:app --host 0.0.0.0 --port 8000

# 3. 前端（构建后用任意静态服务器托管，需把 /api 反代到 8000）
cd ../frontend && npm ci && npm run build
```

> 也可以用镜像里的单容器方案免去 Nginx：把 `frontend/dist` 拷到 `backend/web`，
> 后端会自动同源托管前端（`http://<IP>:8000` 即可访问完整应用）。

## 四、方案 C：只部署前端

零成本、立即可用，适合「先给别人看界面」。

```bash
cd frontend
npm ci
VITE_API_BASE=http://<你的后端地址>/api/v1 npm run build
# 然后把 dist/ 上传到 Cloudflare Pages / Vercel / Netlify
```

**前置条件**：后端必须能被公网访问，且把前端域名加进 CORS 白名单：

```env
SKIN_CORS_ORIGINS=https://your-app.pages.dev,http://localhost:5173
```

后端暴露到公网可以用隧道工具（cpolar / ngrok / frp），或用方案 B 的 VPS。

> ⚠️ 前端是 HTTPS 时，后端也必须是 HTTPS，否则浏览器会拦截混合内容请求。

## 五、方案 D：改用云端 VL API（换掉本地模型）

**实现文档：[`云端API部署.md`](云端API部署.md)。**

这是**绕开全部部署难题**的思路。瓶颈的本质是「本地跑模型」。如果把 Ollama 换成云端多模态 API
（如阿里云百炼的通义千问 VL，国内直连且有免费额度），那么：

- 不再需要显存与那 7 GB 模型
- 512 MB 内存的免费容器就能跑，Render / Fly.io 随便选
- 冷启动从「等模型下载」变成「秒级」

**改造点集中在一处**：`SKIN_LLM_BACKEND=cloud` 时由
`app/services/model_gateway.py` 与 `app/services/llm_factory.py` 分流到云端客户端，
上层编排、检索、安全层不用动。镜像用根目录 **`Dockerfile.cloud`**（不含 Ollama），
附 `render.yaml` / `fly.toml`。

**代价**：图片与文本会上传到第三方，与本项目「数据不出内网」的原始设计前提相冲突。

## 六、公网部署前请确认

1. **隐私边界变了。** 本项目原始定位是本地推理、数据不出内网。部署到公网后，
   用户上传的皮肤照片会离开本机。涉及真实患者数据时请勿使用公网部署方案。
2. **合规边界。** 本系统明确声明「不构成医疗诊断」。公网开放意味着面向不特定人群，
   现有的免责声明与强制就医提示机制是必要条件，但不等于满足医疗器械监管要求——
   若用于诊断目的，需要走相应审批路径。
3. **未做鉴权与限流。** 当前没有 API Key、没有按 IP/会话限流。
   公网暴露时，任何人都能调用你的推理资源（2 核 CPU 很容易被占满）。
   建议至少加一层网关鉴权，或限制访问来源。
4. **免费额度有时限。** 平台免费配额会变化，不要把它当生产依赖。

## 七、排错速查

| 现象 | 原因 | 处理 |
|------|------|------|
| 页面打不开、容器端口不通 | 服务没监听平台要求的端口 | 魔搭必须是 `7860`（8080 被平台占用） |
| 自定义路由 404，静态页面正常 | 静态挂载吞掉了路由 | 确保 `app.mount("/", ...)` 在所有路由注册**之后** |
| 容器报 `bad interpreter: ...bash\r` | `.sh` 被检出成 CRLF | 仓库已配 `.gitattributes`；Dockerfile 里另有 `sed` 兜底 |
| 构建时找不到 `README.md` | `.dockerignore` 误排除了 md 文件 | 确认没排除 `backend/README.md`（pyproject 的 readme 指向它） |
| 重启后知识库变空 | 数据没落在持久化目录 | 确认 `SKIN_DATA_ROOT` 指向挂载卷 |
| 每次重启都重新下载模型 | 模型目录没持久化 | 确认 `OLLAMA_MODELS` 指向挂载卷 |
| 前端能开但请求 404 | 前后端分离部署但 `VITE_API_BASE` 没配 | 构建时传入 `VITE_API_BASE`，并放行 CORS |
| HTTPS 页面请求被浏览器拦截 | 混合内容 | 后端也要走 HTTPS |
| 图片诊断慢到超时 | CPU 跑视觉模型 | 换 3B、降 `SKIN_IMAGE_MAX_SIDE`、或上 GPU |
| 健康面板 `degraded` | 模型未就绪 / 知识库为空 | 按 `warnings` 里的提示逐条处理（提示文案会给出具体命令） |

## 八、一句话建议

- **想免费且国内可访问、尽量本地模型** → 魔搭创空间（[deploy/README.md](../deploy/README.md)）
- **想 512MB 小内存 / 快速公网 Demo** → 云端 VL API + Render/Fly（[云端API部署.md](云端API部署.md)）
- **想认真用、有多人访问** → 一台带 GPU 的 VPS + `docker-compose.yml`，或用云端 VL API
- **只想让人看界面** → 只部署前端（方案 C）
- **在意数据隐私** → 本地跑，不要部署到公网
