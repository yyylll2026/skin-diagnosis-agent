# 登录鉴权方案选型清单

> 本文只做**选型**，不含实现。请圈出要做的项，或直接选第 6 节的一档组合方案。
>
> 起点现状：系统**目前没有任何鉴权**。全部接口匿名可访问，`kb/reset`、`kb/reindex`
> 这类危险操作也是裸奔的（README 里已自我提示「当前尚未做鉴权与限流」）。

---

## 1. 需求映射：两类角色的权限矩阵

先把「角色能做什么」定死，后面所有选型都服务于这张表。

| 能力 | 管理员 | 客户 | 对应现有接口 |
|---|:---:|:---:|---|
| 图文提问 / 知识问答 | ✅ | ✅ | `POST /agent/chat`、`/chat/qa`、`/diagnosis/image` |
| 查看文档列表 | ✅ | ✅ 只读 | `GET /kb/documents` |
| 检索调试 | ✅ | ✅ 只读 | `POST /kb/search` |
| 上传文档 | ✅ | ❌ | `POST /kb/documents` |
| 删除文档 | ✅ | ❌ | `DELETE /kb/documents/{id}` |
| 重建索引 | ✅ | ❌ | `POST /kb/reindex` |
| 清空知识库 | ✅ | ❌ | `POST /kb/reset`（危险） |
| 用户列表 / 创建 / 改角色 / 禁用 / 删除 | ✅ | ❌ | 新增 |
| 重置他人密码 | ✅ | ❌ | 新增 |
| 强制某人下线 | ✅ | ❌ | 新增 |
| 查看审计日志 | ✅ | ❌ | 新增 |
| 查看对话历史 | 全部 / 仅自己（需选） | 仅自己 | `GET /sessions`、`/sessions/{id}` |
| 系统健康检查、模型列表、拓扑图 | ✅ | ✅ | `GET /system/*` |

> ⚠️ **这张表里藏着一个改造量**：现有对话会话（`sessions` 表）只按 `session_id` 存，
> **没有和用户绑定**。要支持「客户只能看自己的历史」，得给 `sessions` 加 `user_id` 外键
> 并在查询处加归属校验——这是本次改动面最大的一块，不是加个装饰器就完事。

## 2. ⚠️ 必须先解决的命名冲突

`MetadataStore` 里已经有一张 `sessions` 表，存的是**对话会话**
（`session_id / title / created_at / updated_at`），对外接口是 `/api/v1/sessions`。

「登录会话」是另一个概念。若也叫 `sessions`，会出现：

- 表名冲突，SQL 无法执行；
- `/api/v1/sessions` 到底是「我的对话列表」还是「我的登录设备」——语义混乱；
- 将来排查问题时要反复确认说的是哪个 session。

**建议命名**（三选一，本文档后续统一用方案 A）：

| 方案 | 登录会话表 | 登录接口前缀 | 说明 |
|---|---|---|---|
| A（推荐） | `auth_sessions` | `/api/v1/auth/*` | 语义最清楚 |
| B | `login_sessions` | `/api/v1/auth/*` | 同上，措辞不同 |
| C | 不改名，`/api/v1/sessions` 让位 | — | 需大规模重命名，不推荐 |

**同时建议把现有的 `sessions` 改名为 `chat_sessions`**（可选），彻底消除歧义——
代价是要改 `db.py`、`chat.py`、`system.py` 和几个测试。

### 四、会话与令牌（**影响面最大的一组，建议优先定**）

| # | 维度 | 选项 | 成本 | 说明 / 建议 |
|---|---|---|---|---|
| D1 | **会话载体** | ① 服务端会话：随机 token 存 SQLite + httpOnly Cookie | 中 | **推荐**。可撤销（管理员能强制下线）、可查询（审计）、无密钥管理 |
| | | ② JWT（access + refresh） | 中 | 无状态、易水平扩展；但**撤销困难**，与「强制下线」需求冲突 |
| | | ③ JWT 放 localStorage + Authorization 头 | 低 | 前端改动最小（现有 axios 加个拦截器即可），但 XSS 可直接窃取令牌 |

| | | ⑤ API Key（长期令牌） | 低 | 适合机器调用，不适合人登录 |
| | | → 建议 | | **①**。本项目单实例、同源托管，Cookie 天然可用；且「可撤销」是硬需求 |

| | | 全部设备登出 | 低 | 建议做 |

## 4. 无论选哪档都必须做的安全底线

这些不是可选项，选哪一档都得做：

1. **密码哈希存储**，绝不存明文，绝不把密码写进日志
2. 密码比较**恒定时间**（`hmac.compare_digest` 或库自带）
3. Cookie 加 `HttpOnly` + `SameSite=Lax`
4. 登录失败**不回显**「用户名不存在」还是「密码错误」（统一提示"用户名或密码错误"，防枚举）
5. **会话校验在服务端**完成，不信任前端传来的角色字段
6. 危险操作（`kb/reset`、删用户）在**服务端**判权限，前端隐藏按钮只是体验
7. 公网部署时必须：`Secure` Cookie + HTTPS + `SKIN_CORS_ORIGINS` 收紧（现在含 localhost 即可，别放 `*`）
8. 会话 token 用 `secrets.token_urlsafe(32)`，不要用 `uuid4` 或时间戳

## 6. 三档组合方案（可以直接选一档）

## 一、开放注册带来的配套要求（与建议不同的那项）

开放注册意味着**任何人都能建号**，因此实现时补了这些必要防护：

1. **角色不可指定**：注册接口的请求模型里**根本没有 `role` 字段**，
   服务端硬编码为 `customer`。构造 `{"role":"admin"}` 提交无效。
   管理员只能由 `scripts/user_cli.py` 创建。
2. **密码强度双重校验**：Pydantic 层要求「同时含字母和数字」，
   服务层再按 `SKIN_AUTH_MIN_PASSWORD_LENGTH`（默认 8）校验长度。
3. **用户名归一化**：统一转小写 + 去空白，避免大小写变体被用来试探用户名。
4. **注册接口也受失败锁定与审计覆盖**（注册冲突会记 `register/conflict`）。

⚠️ **甲档没有邮件服务，所以注册无法做邮箱验证**——账号与实际身份没有绑定关系。
若将来要对外开放，建议补：注册限流、图形验证码、邮箱验证三者之一。

## 三、权限点划分

```
kb:read            客户 ✓  管理员 ✓
kb:write           客户 ✗  管理员 ✓   上传/删除文档
kb:reindex         客户 ✗  管理员 ✓   重建索引
kb:reset           客户 ✗  管理员 ✓   清空知识库（不可恢复）
chat:use           客户 ✓  管理员 ✓
session:read_all   客户 ✗  管理员 ✓   查看他人会话
user:read          客户 ✗  管理员 ✓
user:write         客户 ✗  管理员 ✓
audit:read         客户 ✗  管理员 ✓
```

把 `kb:write` / `kb:reindex` / `kb:reset` 拆成三个权限点，是为了将来能加一个
「能维护文档但不能清库」的知识库编辑员角色，届时不必改任何接口代码。

## 四、为什么没有重命名 `sessions` 表

原计划把「对话会话」表改名为 `chat_sessions` 以消除歧义。实际实施时**暂缓**了：

- 登录会话表命名为 `auth_sessions` 后，两者已无实际冲突；
- 改名需要动 `db.py`、`chat.py`、`system.py` 及若干测试，属于纯改名重构，
  在一个已经涉及 20+ 文件的功能改动里叠加大范围重命名，会显著抬高 review 成本与出错概率。

结论：`sessions`（对话）+ `auth_sessions`（登录）的命名已经足够清晰，改名留作独立的技术债清理项。

## 五、实施中发现并修复的三个真实问题

### 1. 老库升级时建索引会崩（只在已有数据库上暴露）

`_SCHEMA` 里给 `sessions` 加了 `CREATE INDEX ... ON sessions(user_id, ...)`，
但老库的 `sessions` 表**没有** `user_id` 列，而 `CREATE TABLE IF NOT EXISTS` 在老库上是空操作——
于是索引语句在「迁移补列」之前执行，直接报 `no such column: user_id`。

**教训：只测「全新建库」测不出迁移问题。** 新增了 `tests/test_db_migration.py`，
专门构造「老格式库」来覆盖这条路径。首次在生产库上跑 CLI 时正是它挡住了启动。

### 2. 校验错误处理器会 500，且会回显用户提交的密码

`main.py` 的 `RequestValidationError` 处理器直接返回 `exc.errors()`，有两个后果：

- Pydantic 会把原始异常对象放进 `ctx.error`，`JSONResponse` 序列化它直接抛 `TypeError` → 400 变 500；
- `errors()` 里带 `input`（字段原文），**密码校验一失败就把明文密码写进响应体**。

已改为只保留「位置 / 原因 / 类型」三个字段。`test_validation_error_does_not_echo_the_submitted_password` 锁住这个行为。

### 3. 用户名的归一化只写在 schema 里

原实现把「去空白 + 转小写」放在 Pydantic 校验器里，于是 HTTP 之外的调用方（CLI、服务层直调）
会绕过它——`register("  MixedCase  ")` 会存成带空格的混合大小写。
已把实现收敛到 `schemas/auth.py:normalize_username` 一处，服务层与 CLI 都复用它
（service 依赖 schemas 是本项目既定的依赖方向）。

顺带修掉的前端缺陷：`api/index.js` 的 `uploadDocument` 用查询参数传 `category`，
而后端签名是 `Form(...)`，导致分类被静默丢弃、永远落到「其他」。已改为写入 FormData，
实测确认返回 `护理建议`。

## 六、运维方式

```bash
cd backend

# 建管理员（开放注册只能产生客户，管理员必须走这里）
python -m scripts.user_cli create-admin --username root

# 其他命令
python -m scripts.user_cli list
python -m scripts.user_cli set-role    --username bob --role admin
python -m scripts.user_cli set-status  --username bob --status disabled
python -m scripts.user_cli reset-password --username alice
python -m scripts.user_cli audit --limit 30
```

关键配置（`backend/.env`）：

```bash
SKIN_AUTH_ENABLED=true              # 关闭则回到匿名可用的旧行为
SKIN_AUTH_ALLOW_REGISTRATION=true   # 自助注册（角色固定为客户）
SKIN_AUTH_COOKIE_SECURE=false       # 本地 http 必须 false；公网 HTTPS 必须 true
SKIN_AUTH_SESSION_TTL_HOURS=12      # 绝对超时
SKIN_AUTH_IDLE_TIMEOUT_MINUTES=120  # 空闲超时（两者取较小者）
SKIN_AUTH_MAX_FAILED_ATTEMPTS=5
SKIN_AUTH_LOCKOUT_MINUTES=15
SKIN_AUTH_MIN_PASSWORD_LENGTH=8
```

## 七、公网部署前必须补的项

1. `SKIN_AUTH_COOKIE_SECURE=true` + 全站 HTTPS（否则 cookie 明文传输）；
2. `SKIN_CORS_ORIGINS` 收紧到真实域名（**不要**用 `*`，且与 `allow_credentials=true` 不兼容）；
3. 注册接口限流（当前开放注册等于无限建号）；
4. `error_payload` 对非 `AppError` 会透传内部异常文本，应按 `SKIN_DEBUG` 收紧；
5. 反向代理后需把 `_client_ip` 改为读取可信来源的 `X-Forwarded-For`
   （当前只信任直连 IP，是有意为之——该头可被伪造）。
