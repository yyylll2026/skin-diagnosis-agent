## 1. 背景与目标

### 1.1 业务场景

普通用户面对皮肤问题时，痛点集中在三处：**看不懂**（不认识的皮损形态）、
**判断不了轻重**（不知道要不要去医院、要不要挂急诊）、**找不到可信答案**
（网络信息鱼龙混杂，营销内容与伪科普混杂）。

本系统把这两件事串成一条链路：用户上传一张皮肤照片并（可选）补充描述，
系统先做**形态学观察与方向性提示**，再用**本地皮肤科知识库**为结论补上依据，
最后给出护理要点与明确的就医建议。

### 1.2 设计目标

**功能目标**

| 编号 | 目标 | 验收标准 |
|------|------|---------|
| F1 | 知识库问答 | 对皮肤相关文档向量化存储；提问时检索并基于检索结果生成回答，回答带来源引用 |
| F2 | 图片识别 | 接收皮肤照片，调用 Qwen2.5-VL 输出结构化观察结果与疾病方向 |
| F3 | 图文融合 | 图片结论 + 知识库依据合并为一份回答，而非两个独立功能的并列 |
| F4 | 多轮对话 | 同一会话内保持上下文；会话可持久化、可回放、可删除 |
| F5 | 知识库管理 | 文档上传入库、列表、删除、检索调试、全量重建 |

**非功能目标**

| 编号 | 目标 | 指标 |
|------|------|------|
| N1 | 本地化 | 全部推理在本地完成，图片与对话不出内网 |
| N2 | 流式体验 | 文本回答首字延迟 ≤ 3s，逐字输出；图像分析阶段有节点级进度提示 |
| N3 | 鲁棒性 | 模型输出格式异常、Ollama 掉线、向量库为空等场景均给出可读降级结果，不出现白屏 |
| N4 | 可维护性 | 分层清晰、类型标注完整、关键决策有注释说明「为什么」、纯逻辑部分有单测覆盖 |
| N5 | 安全合规 | 任何出口都带免责声明；危险信号由确定性规则兜底扫描，只上调不下调风险等级 |

### 1.3 明确的边界（系统不做什么）

这一节比「做什么」更重要——医疗场景下，边界模糊就是风险。

- **不下诊断结论**。系统输出的始终是「可能的方向」，措辞强制使用「倾向于/需排查」。
- **不开处方、不给剂量**。涉及用药只做方向性说明并引导就医。
- **不替代面诊**。医生能触诊、能用皮肤镜与 Wood 灯、能取病理，照片做不到。
- **不处理非皮肤图像**。检测到非皮肤部位时如实说明并降低所有置信度。
- **不因为 AI 结论而延迟就医**。风险等级达到 high 及以上时，答案开头强制插入就医提示。

```

**依赖方向严格自上而下**：编排层调用服务层，服务层访问数据层；
反向依赖只允许通过「编排层把结果写回状态」来传递。
这条纪律的意义是：任何一层都可以被替换（换向量库、换模型、换前端框架）而不影响其它层。

| 安全服务 | `app/services/safety_service.py` | 确定性危险信号扫描、风险合并、答案合规化 | 不改写医学内容 |

| 节点实现 | `app/agent/nodes.py` | 7 个节点的纯逻辑 | 不碰 HTTP、不碰数据库 |
| 图装配 | `app/agent/graph.py` | 拓扑定义、条件边、编译、Mermaid 导出 | 无业务逻辑 |
| 运行器 | `app/agent/runner.py` | 把框架事件翻译成前端事件协议 | 不关心 HTTP 细节 |
| 路由层 | `app/api/v1/*.py` | 参数组装、调用运行器、响应序列化 | 不含业务判断 |
| 数据访问 | `app/repositories/*.py` | Chroma 与 SQLite 的读写封装 | 不含业务规则 |

## 3. 前后端交互流程

### 3.1 接口清单

| # | 方法 | 路径 | 用途 | 响应形态 |
|---|------|------|------|---------|
| 1 | POST | `/api/v1/agent/chat` | **统一入口**：纯文本 / 图文混合 | SSE 或 JSON |
| 2 | POST | `/api/v1/chat/qa` | 知识库问答（忽略图片字段） | SSE 或 JSON |
| 3 | POST | `/api/v1/diagnosis/image` | 图片识别（multipart 上传） | JSON |
| 4 | POST | `/api/v1/kb/documents` | 上传文档入库 | JSON |
| 5 | GET | `/api/v1/kb/documents` | 已入库文档列表 | JSON |
| 6 | DELETE | `/api/v1/kb/documents/{doc_id}` | 删除文档及其向量 | JSON |
| 7 | POST | `/api/v1/kb/search` | 检索调试（不调 LLM） | JSON |
| 8 | POST | `/api/v1/kb/reindex` | 全量重建索引 | JSON |
| 9 | POST | `/api/v1/kb/reset` | 清空知识库（需 `confirm=true`） | JSON |
| 10 | GET | `/api/v1/system/health` | 各组件就绪状态 | JSON |
| 11 | GET | `/api/v1/system/models` | Ollama 模型及其能力 | JSON |
| 12 | GET | `/api/v1/system/graph` | 智能体拓扑（Mermaid） | JSON |
| 13 | GET | `/api/v1/sessions` | 会话列表 | JSON |
| 14 | GET | `/api/v1/sessions/{id}` | 会话历史回放 | JSON |
| 15 | DELETE | `/api/v1/sessions/{id}` | 删除会话 | JSON |
| 16 | GET | `/` | 服务信息 | JSON |

**为什么把三个对话入口合并到一张图？**
如果为「问答」和「诊断」各写一套编排逻辑，两者会迅速分叉——诊断需要知识库依据、
问答也可能被追问「那照片这样算不算」。统一成一张图后，
「何时检索、何时调视觉模型、何时两者都要」只由 `route` 节点一处决定，
行为天然一致，也避免了双份测试与双份 bug。

### 3.2 链路 A：知识库问答（纯文本）

```
用户          前端              后端 API            LangGraph            数据层
 │             │                   │                    │                 │
 │ 输入问题 ──► │                   │                    │                 │
 │             │ POST /agent/chat  │                    │                 │
 │             │ {session_id,      │                    │                 │
 │             │  message,         │                    │                 │
 │             │  stream:true}     │                    │                 │
 │             ├──────────────────►│                    │                 │
 │             │                   │ 建会话 / 读历史 ──────────────────────►│ SQLite
 │             │                   │ build_state()      │                 │
 │             │                   │ astream_events ───►│                 │
 │             │                   │                    │ preprocess      │
 │             │                   │                    │ route: 命中皮肤关键词
 │             │  event: meta ─────┤◄───────────────────┤                 │
 │             │  event: node ─────┤◄───────────────────┤ (route done)     │
 │             │  event: node ─────┤◄───────────────────┤ build_query      │
 │             │                   │                    │    │            │
 │             │                   │                    │    ▼            │
 │             │                   │                    │ retrieve ──────►│ Chroma
 │             │                   │                    │  (vector+BM25)  │
 │             │  event: sources ──┤◄───────────────────┤                 │
 │             │  event: token ×N ─┤◄───────────────────┤ generate        │
 │             │                   │                    │ safety_review    │
 │             │  event: done ─────┤◄───────────────────┤                 │
 │             │◄──────────────────┤                    │                 │
 │ 渲染回答 ────│  追加来源列表     │                    │                 │
```

**数据流转的关键点**

1. 前端只发送 `message` 与可选的 `image_base64`，**不关心意图**。
   意图由后端 `route` 节点判定后通过 `meta` 事件回传，前端仅用于展示。
2. 会话历史由后端从 SQLite 读取并裁剪（默认最近 6 轮），
   前端不需要维护上下文，也就不会出现「前端历史与后端上下文不一致」的经典问题。
3. 检索到的资料以 `sources` 事件单独下发（而非塞进文本），
   前端据此渲染可折叠的来源列表——**引用溯源与正文解耦**，
   这样回答文本被重新排版时引用不会丢。
4. 完整答案在 `done` 事件上落库，即使客户端中途断开也不会丢历史。

 │            │ event: sources ────┤◄────────────────────────────────────────┤
 │            │ event: token ×N ───┤◄────────────────────────────────────────┤
 │ 渲染建议   ◄┤ event: done ───────┤◄────────────────────────────────────────┤
```

**为什么视觉分析不走流式？**
诊断结果是一个 **JSON 对象**，必须拿到完整内容才能做结构校验与字段归一化；
流式输出的半截 JSON 无法解析，对用户也没有意义。
真正需要「逐字出现」的体感价值在后面的自然语言回答上，所以**结构化阶段批处理、
生成阶段流式**——这是一个刻意的分工，不是遗漏。

**降级路径**：视觉调用失败时**不抛出中断整图**，而是把错误写入 `errors` 并令
`vision=None`，后续走纯文本问答路径。用户至少能得到一个基于知识库的回答，
而不是一片空白。

### 3.5 SSE 事件协议

前端用 `fetch` + `ReadableStream` 消费（因为需要 POST 带 JSON body，
原生 `EventSource` 只支持 GET，无法承载图片 base64）。

| 事件 | 时机 | 载荷 | 前端动作 |
|------|------|------|---------|
| `meta` | 受理时；`route` 完成后 | `{session_id, has_image, nodes, intent?}` | 初始化气泡、显示意图 |
| `node` | 每个节点开始/结束 | `{node, label, status, elapsed_ms?}` | 刷新「正在做什么」进度 |
| `vision` | `vision_analyze` 完成 | 完整 `VisionDiagnosis` | 内嵌渲染诊断卡片 |
| `sources` | `retrieve` 完成 | `RetrievedChunk[]` | 底部渲染参考来源 |
| `token` | 生成中逐块 | `{text}` | 追加到气泡 |
| `answer` | token 流缺失时兜底 | `{text}` | 整段覆盖（补偿） |
| `done` | 全流程结束 | `{answer, safety, elapsed_ms, errors}` | 收尾、展示风险等级 |
| `error` | 任意阶段异常 | `{code, message}` | 错误态 + 解锁「生成中」 |

`event:` 与 `data:`（JSON）成对出现，以 `\n\n` 分隔。
服务端每 15 秒发一次心跳注释行，防止中间层（Nginx / 代理）因空闲而断开长连接。

### 3.6 请求/响应契约要点

```jsonc
// POST /api/v1/agent/chat 请求
{
  "session_id": "s-3f9a2b1c4d5e",   // 可为 null，后端生成并回传
  "message": "这块红斑有两个月了，有点痒",
  "image_base64": "iVBORw0KGgo...",  // 可带 data URI 前缀，后端会剥掉
  "image_mime": "image/jpeg",
  "use_knowledge": true,             // false = 跳过检索，直连生成
  "stream": true
}
```

```jsonc
// GET /api/v1/system/health 响应（注意：永不返回 5xx）
{
  "status": "degraded",              // ok | degraded
  "ollama_connected": true,
  "vision_model": "qwen2.5vl:7b",
  "vision_model_ready": true,
  "embedding_model": "bge-m3",
  "embedding_model_ready": false,
  "indexed_chunks": 0,
  "indexed_documents": 0,
  "warnings": ["向量模型未就绪，请执行：ollama pull bge-m3"]
}
```

> **设计取舍**：健康检查即使依赖不可用也返回 HTTP 200，把问题写进 `warnings`。
> 因为它是**诊断面板**而不是**存活探针**——若返回 5xx，前端只会显示「服务异常」，
> 用户根本看不到「请执行 ollama pull bge-m3」这种可直接照做的修复指引。

### 3.7 状态流转（AgentState 生命周期）

| 阶段 | 写入字段 | 读取字段 | 谁可能跳过 |
|------|---------|---------|-----------|
| 入参 | `session_id/history/question/image_bytes/image_mime/use_knowledge` | — | — |
| `preprocess` | `question`（净化）、`image_bytes`（解码后）、`image_meta`、`errors` | `image_bytes` | — |
| `route` | `intent` | `question`、`image_bytes` | — |
| `vision_analyze` | `vision`、`errors` | `image_bytes` | 纯文本 / 闲聊 |
| `build_query` | `queries` | `vision`、`question` | 闲聊 |
| `retrieve` | `sources`、`context`、`errors` | `queries` | 闲聊 / 关闭知识库 |
| `generate` | `answer` | `vision`、`context`、`history` | — |
| `safety_review` | `answer`（合规化）、`safety` | `answer`、`question`、`vision` | — |
| `timings` | 每个节点追加自身耗时 | — | — |

**状态是单次请求级的**：图片是体积较大的二进制对象，若把整条状态塞进
LangGraph 的 checkpointer，存储会迅速膨胀，而我们并不需要跨请求复用图片。
因此会话历史由 SQLite 承载、按需注入 `history` 字段，跑完即弃。

## 4. 知识库构建与检索链路

### 4.1 链路总览

```
        ┌── 离线：入库 ──────────────────────────────────────────────┐
        │                                                            │
 PDF/DOCX/MD/TXT/HTML                                              
        │                                                            │
        ▼                                                            │
   ┌─────────┐   ┌─────────┐   ┌────────────┐   ┌──────────┐   ┌────▼─────┐
   │ 解析     │──►│ 清洗     │──►│ 分块        │──►│ 向量化    │──►│ Chroma   │
   │ 按格式   │   │ 控制字符 │   │ 600/100    │   │ bge-m3   │   │ + SQLite │
   │ 保留页码 │   │ 修 CJK 空格│  │ 中文分隔符  │   │ 1024 维   │   │ 登记     │
   │         │   │ 压空行   │   │ 标题路径    │   │          │   │          │
   └─────────┘   └─────────┘   └────────────┘   └──────────┘   └──────────┘
        │                                                            │
        └────────────────────────────────────────────────────────────┘

        ┌── 在线：检索 ──────────────────────────────────────────────┐
        │                                                            │
   query ──┬──► 向量召回（余弦 Top-8）      ──┐                        │
           │                                ├──► RRF 融合 ──► 阈值过滤 ──► 可选 LLM 重排 ──► Top-4
           └──► BM25 召回（jieba 分词 Top-8）┘                        │
        │                                                            │
        └────────────────────────────────────────────────────────────┘
```

**为什么是双路召回而不是纯向量？**
纯向量的失效模式很典型：疾病名、药物名、缩写这类**专有名词**，
语义向量会把它们编码到相近但不等价的邻域。用户问「是不是带状疱疹」，
向量可能召回一堆「病毒性皮疹」的泛泛描述；而 BM25 能精确命中「带状疱疹」四个字。
反之，用户描述「脸上起了红色的小疙瘩」，文档里写的是「面部丘疹性皮损」，
只有向量能跨过用词差异。**两路的失效模式互补，所以都要。**

### 4.2 文档处理

**解析**：支持 PDF / DOCX / Markdown / TXT / HTML 五种格式。

| 格式 | 解析方式 | 元数据保留 |
|------|---------|-----------|
| PDF | `pypdf` 逐页提取 | `page`（页码，用于溯源） |
| DOCX | `python-docx`，段落 + 表格（表格行拍平成 `a \| b \| c`） | — |
| Markdown | 直接读原文，保留 `#` 结构 | 章节路径 |
| TXT | 编码回退读取（utf-8 → utf-8-sig → gbk → 忽略错误） | — |
| HTML | `BeautifulSoup` 剔除 script/style/nav/footer，取正文，标题转 Markdown | 章节路径 |

> **不引入 LangChain Community 的 DocumentLoader**：其依赖面极广
> （unstructured、pdfminer、多种图像库），本地部署装起来慢且易版本冲突。
> 本项目只需 5 种格式，手写解析更可控。分块仍复用 LangChain 的
> `RecursiveCharacterTextSplitter` / `MarkdownHeaderTextSplitter`，保持抽象一致性。

**清洗**（`clean_text`）三件事：

1. 去除控制字符（PDF 抽出的文本常混入 `\x00` 等）；
2. **修复汉字之间被插入的空格**（PDF 抽取的典型问题），
   同时**保留英文单词之间的空格**——用 `(?<=[\u4e00-\u9fff])\s+(?=[\u4e00-\u9fff])` 精确匹配；
3. 连续空行压成单空行。

**分块策略**：

- 参数：`chunk_size=600`、`chunk_overlap=100`。
  600 字的依据是——皮肤科文档的一个完整知识点（一条疾病特征的描述）
  大致在这个量级，再大会让单个向量混入多个主题，再小会割裂上下文。
  100 字重叠用于避免「关键句正好被切在边界」。
- 分隔符优先级：`["\n\n", "\n", "。", "！", "？", "；", "，", "、", "：", " ", ""]`。
  **中文标点必须在空格之前**，否则中文会被按空格切碎。
- **Markdown 两级切分**：先用 `MarkdownHeaderTextSplitter` 按 `#/##/###` 切，
  把标题路径写入 `section`，再做字符递归切分。
  这样「为什么要保湿」这句话在「湿疹」节下和在「银屑病」节下能被区分开。
- 丢弃长度 < 20 字的碎片（通常是页眉页脚残留）。

**块元数据 schema**：

| 字段 | 说明 |
|------|------|
| `chunk_id` | `{doc_id}::{chunk_index}`，Chroma 主键，用于跨路去重 |
| `doc_id` | 文件内容 SHA1 前 16 位 |
| `title` / `source` / `category` | 标题 / 原文件名 / 分类（支持检索期过滤） |
| `page` / `section` | 页码 / 章节路径（用于引用溯源） |
| `chunk_index` | 文内序号（展示与调试） |
| `content_hash` | 块内容 SHA1（去重与调试） |
| `ingest_time` | 入库时间 |

> **doc_id 用内容哈希而非 UUID**：同一份文件重复上传天然幂等，
> 文档改版后重新上传即覆盖旧版本，不会在库里留下孤儿向量。

### 4.3 向量化

| 项 | 选择 | 理由 |
|----|------|------|
| 首选模型 | `bge-m3`（Ollama 托管，1024 维） | 多语言、中文语义效果好；与推理模型共用一套 Ollama 部署，零额外运维 |
| 备选 | `BAAI/bge-small-zh-v1.5`（sentence-transformers） | 不依赖 Ollama 时的本地方案，需装 `[hf]` extra |
| 兜底 | Chroma 内置 ONNX MiniLM | 零配置，用于冒烟验证；**中文效果一般，不建议生产** |

后端通过 `SKIN_EMBEDDING_BACKEND` 切换，业务代码零改动（工厂模式）。

> ⚠️ **一致性约束（高频踩坑点）**：Chroma 集合的向量维度在**首次创建时固定**。
> 更换 embedding 模型后若不重建，写入与查询会直接抛维度不匹配错误。
> 因此 CLI 与接口都提供 `reindex`，并在文档与 `health` 提示中反复强调。

### 4.4 存储

**Chroma（向量）**

| 配置 | 值 | 理由 |
|------|-----|------|
| 客户端 | `PersistentClient` | 本地部署无需独立服务，sqlite3 + hnswlib 落盘，零运维 |
| 距离空间 | `hnsw:space = cosine` | 短文本片段用余弦比 L2 稳定；且余弦距离可线性映射到 0~1 相关度，便于前端展示 |
| 集合名 | `skin_kb` | 可配置，便于同一实例挂多套知识库 |
| 主键 | `{doc_id}::{chunk_index}` | 幂等覆盖；删除按 `where={"doc_id": ...}` |

**SQLite（元数据）**：三张表，职责单一，不用 ORM。

| 表 | 用途 |
|----|------|
| `documents` | 文档登记：`doc_id / title / source / category / chunk_count / size_bytes / created_at` |
| `sessions` | 会话：`session_id / title / created_at / updated_at` |
| `messages` | 消息：`id / session_id / role / content / has_image / created_at`（含 `idx_messages_session` 索引） |

> 之所以拆成「向量库 + 关系库」两套存储：向量检索需要 HNSW 索引，
> 关系查询需要事务与聚合。**用一个库硬扛两件事**，要么放弃索引效率，
> 要么把业务表塞进向量库的 metadata 里，两者都得不偿失。
> 二者通过 `doc_id` 关联，边界清晰。

### 4.5 检索策略

**第 1 步：双路召回**（每路 Top-8）

- 向量路：`similarity_search_with_relevance_scores`，得到余弦相关度（0~1）
- 关键词路：`BM25Okapi`，语料为全库分块，**用 jieba 分词**，
  并注入约 90 个皮肤科领域词（疾病名、形态学术语、部位、诊疗操作）

> **中文 BM25 的坑**：`rank_bm25` 默认按空格切词，中文整句会变成一个 token，
> 关键词召回直接失效。必须分词；且必须加领域词典——不加的话 jieba 会把
> 「银屑病」切成「银屑/病」、「特应性皮炎」切成「特应/性/皮炎」，召回质量断崖式下降。

**第 2 步：RRF 融合**

$$\text{score}(d) = \sum_{r \in \{vec,\ bm25\}} \frac{w_r}{k + \text{rank}_r(d)}, \quad k = 60$$

**RRF 解决的是「两路分数不可比」的问题**：余弦相似度是有界的 0~1，
BM25 分数是无界的 TF-IDF 加权和。直接加权求和需要凭经验调缩放系数，
换一批语料就得重调；RRF 只用排名不用分数，天然规避量纲问题。
`k=60` 取自原论文经验值，作用是压平头部差异——避免某一路的 top-1
因为「恰好排第一」而获得过高权重。

**多查询融合**：融合层会产出最多 3 条 query（疾病方向 / 形态特征 / 风险处置），
每条 query 各自跑双路召回，**全部投入同一个 RRF 池**。
查询之间按顺序降权（1.0 / 0.8 / 0.6），体现「第一条最贴近用户真实意图」。

**第 3 步：阈值过滤与重排**

- **展示分与排序分分离**（一个刻意的设计）：
  - **排序**用 RRF 分（鲁棒）
  - **展示**用加权混合分 `0.6 × 余弦 + 0.4 × 归一化BM25`（直观，用户能理解「相关度 72%」）
- 混合分低于 `min_relevance=0.15` 的命中被丢弃，
  宁可返回「资料未涵盖」也不拿不相关内容去污染回答。
- **可选 LLM 重排**（`SKIN_RERANK_ENABLED`，默认关闭）：
  把候选片段编号后交给轻量模型打分。**任何失败都静默回退到 RRF 顺序**——
  重排是加分项，不能成为单点故障。默认关闭的原因是本地 7B 模型重排一次
  要增加 5~15 秒延迟，收益与代价需要按场景权衡。

**第 4 步：上下文预算**

注入提示词的资料总长度上限 4000 字符（`CONTEXT_CHAR_BUDGET`）。
超出部分直接丢弃尾部（已按相关度排序，尾部损失最小）。
原因是本地模型 `num_ctx=8192`，若资料占满会挤掉对话历史与生成空间，
表现为「回答被截断」这类难以定位的问题。

**第 5 步：上下文格式化**

检索结果拼成带编号的参考资料块（`[1] 《文档标题》（分类：…）第 N 页 + 片段`）。
编号是给模型做脚注引用的锚点，前端按同样顺序渲染 `sources`，两边对得上。

### 4.6 知识库生命周期

| 操作 | 行为 | 幂等性 |
|------|------|--------|
| 上传入库 | 落盘 → 解析 → 分块 → 先按 `doc_id` 删旧向量 → 写入新向量 → 登记元数据 | ✅ 同内容重复上传 = 覆盖 |
| 删除文档 | 清向量（`where doc_id`）+ 删登记 + 删上传文件 | ✅ |
| 全量重建 | 清空集合 → 重新扫描 `data/docs/` 入库 | ✅ |
| 清空 | 需显式 `confirm=true` | ✅ |

> 删除时**只清索引，不删人工投放到 `data/docs/` 的原始语料**——
> 避免误删用户手工整理的资料。而运行时上传的文件放在 `data/uploads/`，
> 与人工语料物理隔离，删除时会连带清理。这是「可恢复优于不可逆」原则的体现。

## 5. 图片识别与文本问答的融合

### 5.1 融合要解决的问题

把图片识别与文本问答做成两个独立按钮，是这类系统最常见的偷懒做法，
后果是**两个半成品**：

| 只有视觉 | 只有检索 | 融合后 |
|---------|---------|--------|
| 「看起来像湿疹」——没有依据、没有护理建议、没有就医时机，用户拿到的是半成品 | 用户上传了图却不知道该输入什么关键词，检索无从下手 | 视觉把图像映射成医学术语 → 检索拿到依据 → 生成有据可依的回答 |

### 5.2 两级语义映射

融合的本质是**两次空间映射**：

```
  图像空间                    医学语义空间                   知识空间
 ┌────────┐                ┌──────────────┐             ┌──────────────┐
 │ 像素    │  Qwen2.5-VL   │ 红斑/丘疹     │  Chroma     │ 皮肤科文档    │
 │ 颜色    │ ────────────► │ 面部/对称     │ ──────────► │ 病因/鉴别/护理│
 │ 纹理    │   视觉理解      │ 湿疹(0.62)    │   向量检索   │ 就医指征      │
 │ 形态    │                │ 接触性皮炎(0.28)│            │              │
 └────────┘                └──────────────┘             └──────────────┘
```

**第一次映射（视觉 → 语义）**的价值在于：它把「这张图看起来像什么」
翻译成了**可以与知识库匹配的词汇**。这一步是整个融合能成立的物理基础——
没有它，知识库再全也无从检索。

**第二次映射（语义 → 知识）**的价值在于：它给结论装上了依据。
更重要的是，检索到的资料会**反向约束生成的措辞**——
模型从「自由的视觉描述」收敛到「引用编号的科普回答」，幻觉空间被显著压缩。

### 5.3 统一调度：意图 × 模态 决策矩阵

| 用户输入 | `route` 判定 | 是否调视觉 | 检索 query 来源 | 生成链 |
|---------|-------------|-----------|----------------|--------|
| 仅文本，含皮肤关键词 | `kb_qa` | ✗ | 用户问题本身 | 知识库问答链 |
| 仅文本，寒暄 | `chitchat` | ✗ | 不检索 | 闲聊链 |
| 图片（无文字） | `image_diagnosis` | ✓ | 视觉结果生成 3 条 | 融合链 |
| 图片 + 文字 | `image_diagnosis` | ✓ | 视觉结果 + 用户文本 | 融合链 |
| 图片 + `use_knowledge=false` | `image_diagnosis` | ✓ | 不检索 | 融合链（context 为空） |

**路由决策顺序**（规则优先，因为本地 LLM 调用一次要 1~2 秒，
而 90% 的情况用关键词就能判准）：

1. 有图片（且预处理成功）→ `image_diagnosis`。**图片优先级最高**：
   一张图携带的信息量远大于一句文字描述，且用户上传图片的意图非常明确。
2. 无文本 → `chitchat`。
3. 命中皮肤关键词（约 60 个）→ `kb_qa`，**跳过 LLM 分类，省 1~2 秒**。
4. 匹配寒暄模板（正则）→ `chitchat`。
5. 其余交给轻量模型分类，**失败则回落到 `kb_qa`**（宁可多检索，不可漏答）。

### 5.4 融合查询构造

**首选 LLM 生成**（`QUERY_BUILD_PROMPT`，用 fast 模型）：

```
输入：视觉分析结果 JSON + 用户原始问题
输出：["湿疹 病因 表现 鉴别", "面部 淡红 丘疹 鳞屑 常见疾病", "皮肤 危险信号 就医指征"]
```

**确定性兜底**（`_fallback_queries`）：LLM 不可用或输出异常时，
直接用结构化诊断里的字段拼 query——结构化结果本身已经带了疾病名与形态学术语，
足够拼出可用的检索词。**这保证了融合链路不存在「模型挂了就整条断」的单点。**

### 5.5 融合生成的输出结构

`FUSION_SYSTEM_PROMPT` 强制五段式结构，每段都有明确的信息来源约束：

| 段落 | 内容 | 事实来源 |
|------|------|---------|
| 观察到的表现 | 2~4 条客观观察（部位/形态/颜色/分布/尺寸） | 视觉结果，**只描述看得见的** |
| 可能的方向 | 1~3 个方向，各带依据 + 置信度，明示「可能性而非诊断」 | 视觉结果 |
| 相关知识 | 常见诱因、需要鉴别的疾病，带脚注引用 | **仅知识库资料** |
| 需要留意 | 逐条列出危险信号与就医建议 | 安全规则 + 视觉 red_flags |
| 下一步建议 | 日常护理要点 + 明确的就医时机与科室 | 知识库资料 |

硬性约束写在提示词里，并**由代码二次保证**：不下诊断结论、
不用绝对化表述、资料未覆盖就直说、结尾免责声明由系统自动追加
（不依赖模型每次都记得写）。

### 5.6 三种输入组合的处理差异

| 组合 | 视觉分析 | 检索 | 生成 | 与其它组合的区别 |
|------|---------|------|------|----------------|
| 纯文本 | 跳过 | ✓ | 知识库问答链 | 无视觉结论，回答全靠资料 |
| 纯图片 | ✓ | ✓（3 条 query） | 融合链 | 无用户文字，`question` 用默认提示词 |
| 图文混合 | ✓ | ✓（视觉 + 文本 query） | 融合链 | 用户文字作为视觉判断的**参考而非依据** |

> 提示词里明确写了「用户补充的文字描述仅作参考，不可当作确诊依据，也不要盲从」——
> 因为用户的自我描述经常不准确（把银屑病说成「过敏」、把带状疱疹的痛说成「肌肉拉伤」），
> 若让文字凌驾于图像证据之上，会把系统带偏。

## 6. 关键设计决策（ADR 摘要）

| # | 决策 | 备选 | 选择理由 | 付出的代价 |
|---|------|------|---------|-----------|
| D1 | 用 LangGraph 状态图编排 | 手写 if/else 流程 | 分支可视化、节点可单测、新增输入组合不改拓扑、天然支持流式事件 | 引入框架依赖与学习成本 |
| D2 | 三条链路汇流到同一张图 | 问答/诊断各一套 | 行为一致、单份测试、新增能力只改一处 | 单点复杂，需靠节点拆分保持可读 |
| D3 | 视觉走 Ollama REST 而非 `ChatOllama` | 全用 LangChain 封装 | REST 可传 `format` 做 JSON Schema 语法约束，这是结构可靠性的关键；且规避了 LangChain 多模态消息在版本间的行为差异 | 多一层薄适配代码 |
| D4 | 结构化输出「三级降级」 | 只用一种方式 | 不同模型对 `format` 的支持不一致；降级保证任何模型都能跑，且每次降级有日志可查 | 失败时多花一次推理 |
| D5 | 视觉分析不流式 | 视觉也流式 | JSON 必须完整才能校验；半截 JSON 无意义 | 视觉阶段需等待（用节点进度缓解） |
| D6 | 会话历史放 SQLite 而非 checkpointer | `MemorySaver`/`SqliteSaver` | 会话需可查、可删、可回放；图片体积大不宜持久化；避免版本兼容问题 | 需自己维护历史表 |
| D7 | 双路召回 + RRF | 纯向量 / 加权求和的混合 | 专有名词与语义改写两种失效模式互补；RRF 免去量纲调参 | 需维护 BM25 内存索引 |
| D8 | 排序分与展示分分离 | 统一用 RRF 或统一用混合分 | RRF 鲁棒但数值不直观，混合分直观但易被单路污染；各取所长 | 需向使用者解释两者区别 |
| D9 | LLM 重排默认关闭 | 默认开启 | 本地 7B 重排增加 5~15s 延迟；检索质量在多数场景已够用 | 高精度场景需手动开启 |
| D10 | 安全层用确定性规则 | 让 LLM 自检 | 模型的安全意识是概率性的（十次里可能两次轻描淡写），医疗场景不可接受 | 规则需人工维护与扩充 |
| D11 | 风险等级只上调不下调 | 取模型与规则的均值 | 保守优先，宁可误报不可漏报 | 可能对轻微情况过度提示 |
| D12 | 健康检查永不返回 5xx | 依赖不可用即 503 | 它是诊断面板不是存活探针，必须让用户看到**可操作的修复指引** | 不适合直接用作 K8s liveness probe（应另设端点） |
| D13 | 不用 ORM，直接用 sqlite3 | SQLAlchemy | 只有 8 个简单语句，省掉重量级依赖与 ORM 心智负担 | 语句需手写，复杂查询会吃力（当前无此需求） |
| D14 | 提示词与 Schema 同源 | 手写字段清单 | 从 Pydantic 模型生成 JSON Schema，杜绝「提示词写了 6 个字段、代码改了 7 个」的漂移 | 提示词可读性略降 |
| D15 | 前端自建 SSE 解析（fetch） | 原生 `EventSource` | 需要 POST + JSON body（图片 base64），`EventSource` 只支持 GET | 需自行处理跨 chunk 断裂与流式解码 |
| D16 | `num_ctx` 显式抬到 8192 | 用 Ollama 默认值 | 默认仅 2048~4096，RAG 长上下文会被**静默截断**，表现为「答案莫名丢失依据」 | 显存占用上升，需按硬件调整 |

## 7. 安全与合规

医疗辅助系统的安全设计不能是「提示词里写一句请不要乱说」，
必须是**多层、代码强制、可测试**的。本系统的三层防线：

```
第 1 层 提示词约束（软）        第 2 层 结构约束（中）        第 3 层 规则兜底（硬）
├─ 不得确诊                    ├─ JSON Schema 语法约束       ├─ 22 条危险信号关键词规则
├─ 不得开方/给剂量              ├─ Pydantic 结构校验          ├─ 紧急词库 → urgent
├─ 证据不足要说明              ├─ 枚举归一化（防绕过）        ├─ 只上调不下调风险等级
├─ 危险信号必须上报             ├─ 置信度夹紧到 0~1          └─ 免责声明 + 就医横幅由代码注入
└─ 不用绝对化表述
```

### 7.1 为什么第 3 层必须是规则

模型的安全意识是**概率性**的：同一张图问十次，可能八次提示就医、两次轻描淡写。
医疗场景下这种不确定性不可接受。因此用**关键词规则表**做确定性扫描，
与模型自述的 `red_flags` **取并集**，再按严重度取最大值。

### 7.2 危险信号规则表（节选）

| 关键词 | 触发的风险提示 |
|--------|--------------|
| 不对称 / 边界不规则 / 颜色不均 | 皮损形态符合色素性病变危险征象 |
| 迅速增大 / 快速扩大 | 皮损短期迅速变化，需尽快就诊 |
| 破溃 / 溃疡 | 存在破溃或溃疡，需尽快明确性质 |
| 出血 / 渗液 / 化脓 | 需警惕感染或恶变 |
| 水疱 / 大疱 / 尼氏征 | 需警惕大疱性皮肤病或重症药疹 |
| 黏膜 | 累及黏膜，需尽快就诊 |
| 发热 / 关节痛 | 需警惕全身性感染或系统性疾病 |
| 呼吸困难 | 属急症，请立即就医 |
| 大面积 / 全身 | 皮损泛发，需尽快评估 |
| 紫癜 / 网状青斑 | 需排查血液系统及血管性疾病 |

`URGENT_LEXICON`（呼吸困难、大疱、尼氏征、大面积、全身、迅速增大）
命中时风险等级**直接判为 urgent**。

### 7.3 风险等级合并算法

```
输入：视觉模型给出的 risk_level、视觉 red_flags、规则扫描命中项、用户文本、生成答案
  │
  ├─ 1. 扫描范围 = 用户文本 + 视觉 summary/image_quality/red_flags/形态描述 + 生成的答案
  ├─ 2. red_flags = 模型自述 ∪ 规则命中（去重、截断到 8 条）
  ├─ 3. base = 视觉 risk_level（无视觉则 low）
  ├─ 4. 若规则命中 → base = max(base, high)        ← 只上调
  ├─ 5. 若命中紧急词库 → level = urgent             ← 再上调
  └─ 6. must_see_doctor = red_flags 非空 或 level ≥ high
```

**单调性是可以被单测断言的**（`tests/test_safety.py::test_risk_level_is_never_downgraded`）：
规则永远不会把模型判定的 `high` 降下来。这是安全层最核心的不变量。

### 7.4 答案合规化（`augment`）

- 需要就医时，答案**开头**插入醒目提示（`> ⚠️ **请尽快就医**…`）；
- 结尾追加免责声明 `DISCLAIMER`；
- **幂等**：免责声明已存在时不重复追加——多轮拼接场景下这一点很关键，
  否则第 3 轮回答会挂着 3 份免责声明。

### 7.5 数据隐私

- 全部推理在本地完成，图片与对话不出内网；
- 图片默认**不落盘**（流式入口仅在内存中处理），仅记录 `has_image` 标记；
- 上传的**文档**落盘到 `data/uploads/`，删除文档时连带清理；
- 会话历史存本地 SQLite，可通过接口彻底删除；
- 日志中不记录图片内容，仅记录尺寸、体积与耗时。

## 8. 部署方案

### 8.1 本地开发（当前形态）

```
终端 1                             终端 2
┌──────────────────────┐          ┌──────────────────────┐
│ ollama serve         │          │ cd frontend          │
│ (11434)              │◄─────────│ npm run dev (5173)   │
└──────────┬───────────┘          └──────────┬───────────┘
           │                                 │  /api 代理
           │                                 ▼
           │                      ┌──────────────────────┐
           └──────────────────────┤ uvicorn app.main     │
                                  │ (8000)               │
                                  └──────────────────────┘
```

Vite 通过 `server.proxy` 把 `/api` 转发到 `127.0.0.1:8000`，
从而**开发期同源**，绕开浏览器跨域限制（生产期由 Nginx 承担同一职责）。

### 8.2 容器化

`docker-compose.yml` 提供 backend + frontend 两个服务，
Ollama 默认跑在宿主机（Windows/macOS 上能直接用 GPU，
容器内跑 Ollama 的 GPU 透传在 Windows 上体验较差），
通过 `host.docker.internal:11434` 访问，并配了 `extra_hosts` 兼容 Linux。
需要把 Ollama 也容器化时，启用文件中注释的 `ollama` 服务即可。

后端 Dockerfile 用**多阶段构建**：builder 阶段装 build-essential 编译依赖，
运行阶段只拷贝 `/install` 与代码，镜像更小、攻击面更窄。

### 8.3 资源与性能基线（参考值，随硬件浮动）

| 环节 | 典型耗时 | 说明 |
|------|---------|------|
| 图像预处理 | 0.1~0.3s | Pillow 缩放 + 重编码 |
| 视觉分析（7B, q4, GPU） | 8~25s | 受分辨率与输出长度影响 |
| 视觉分析（7B, q4, CPU） | 60~180s | **强烈建议用 GPU**；可用 `qwen2.5vl:3b` 提速 |
| 检索（双路 + RRF） | 0.1~0.5s | 纯 CPU，BM25 索引常驻内存 |
| 文本生成（7B, GPU） | 15~40 tok/s | 首字延迟 1~3s |
| 整链路（图片 + 问答） | 20~60s | 主要是两次模型推理 |

**加速手段**：`keep_alive=30m` 保持模型常驻显存，避免每次请求重新加载（首次加载几十秒）；
`num_ctx` 按需下调；纯文本场景可把 `SKIN_TEXT_MODEL` 换成更小的纯文本模型。

### 8.4 生产化改造建议

当前形态是「单机 + 本地模型」，上生产需要补：

| 方向 | 改造点 |
|------|--------|
| 水平扩展 | 检索与生成分离部署；Ollama 换成 vLLM/TGI 以支持并发批处理 |
| 存储 | Chroma → Milvus/Qdrant（支持分布式与更大规模）；SQLite → PostgreSQL |
| 鉴权 | 增加 API Key / OAuth2；接口按租户隔离知识库（`collection` 加租户前缀） |
| 限流 | 按会话与 IP 限流，防止单个用户占满推理资源 |
| 幂等与重试 | 长耗时接口改为「提交任务 → 轮询/推送结果」的异步模式 |
| 审计 | 记录每次诊断的输入摘要、模型版本、输出哈希，满足可追溯要求 |
| 合规 | 明确医疗器械分类边界；若用于诊断目的需走 NMPA 审批路径 |

## 9. 可观测性与性能

### 9.1 埋点

| 层次 | 埋点 | 用途 |
|------|------|------|
| HTTP | `X-Elapsed-Ms` 响应头；>5s 的请求打 WARNING 日志 | 定位慢接口 |
| 节点 | `state["timings"][node_name]`，随 `node` 事件下发 | 定位慢节点（是检索慢还是生成慢） |
| 检索 | 命中条数、RRF 分与混合分、重排是否触发 | 调分块与权重 |
| 视觉 | 图像尺寸变化、体积变化、是否降级、使用了哪级 format 策略 | 定位模型兼容性问题 |
| 安全 | 风险等级、强制就医标记、危险信号条数 | 安全审计 |
| Token | `on_chat_model_stream` 逐块事件 | 流式体验评估 |

日志用 loguru 输出彩色控制台 + 按天切分落盘（保留 7 天，`enqueue=True` 保证多线程安全）。

### 9.2 性能瓶颈与优化

| 瓶颈 | 表现 | 优化手段 |
|------|------|---------|
| 视觉推理 | 单张图 10~180s | GPU；降分辨率到 1024；用 3b 模型；限制 `num_predict` |
| 串行多查询检索 | 3 条 query 顺序检索 | 目前向量库在本地，0.5s 内完成，暂不必并行；上规模后改 `asyncio.gather` |
| BM25 索引重建 | 全库重建在大语料下变慢 | 已用「count 变化」作为版本号懒加载；更大规模应换 ES/OpenSearch |
| 上下文过长 | 生成变慢、回答被截断 | 4000 字符预算 + `rerank_top_n=4` 双重限制 |
| 模型热加载 | 首个请求极慢 | `keep_alive=30m` + 启动预热（Chroma 建集合、图编译） |

### 9.3 启动预热

应用 lifespan 中主动调用 `warmup()`：建立 Chroma 集合、编译状态图。
否则这些开销会全部落在**第一个用户的请求**上，体验上表现为「首问超时」。
预热失败不阻止启动（记 WARNING），保证 Ollama 未启动时服务仍可起来并回报状态。

## 10. 测试策略

| 层次 | 文件 | 覆盖内容 | 是否依赖 Ollama |
|------|------|---------|---------------|
| 解析 | `test_parsing.py` | JSON 提取（围栏/前言/尾随逗号/Python 字面量/字符串内括号）、结构收敛、置信度归一化、中文风险等级、Schema 展开 | ✗ |
| 安全 | `test_safety.py` | 风险等级单调性、规则兜底、紧急词库升级、危险信号去重、免责声明幂等 | ✗ |
| 入库与检索 | `test_ingest_and_retrieval.py` | 文本清洗（CJK 空格）、各格式解析、分块元数据与章节、分块大小约束、jieba 领域词典、RRF 数学性质 | ✗ |
| 路由 | `test_agent_routing.py` | 意图判定优先级、条件边分支、图片解码容错、data URI 兼容 | ✗ |
| 接口 | `test_api.py` | 路由注册、OpenAPI 生成、健康检查 200 语义、404/400 错误语义、耗时头 | ✗（仅探活） |

**测试设计的取向**：全部用例都**不依赖 Ollama**。
理由是模型推理慢、结果不确定，把它塞进单测会让 CI 变得又慢又脆。
因此测试集中覆盖三类最适合单测的东西：
① 纯函数逻辑（解析、清洗、分块、RRF）；② 安全不变量（可精确断言）；
③ 接口契约（路由与错误语义）。
模型效果本身属于**评估**范畴，应另建带标注集的评测流程，而不是混进单测。
