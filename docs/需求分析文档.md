## 第一部分 项目总体说明

### 1.1 项目背景

普通用户面对皮肤问题时存在三处痛点：**看不懂**（不认识皮损形态）、**判断不了轻重**（不知道该不该去医院）、**找不到可信答案**（伪科普与营销内容混杂）。传统搜索引擎返回的内容质量参差，通用大模型缺乏皮肤科领域知识约束，回答容易"自由发挥"而缺乏依据。

本项目基于 **Ollama（Qwen2.5-VL 视觉语言模型）+ LangGraph + Chroma + FastAPI + Vue 3**，构建一个本地化部署的皮肤诊断辅助系统。系统支持**知识库问答**与**图片识别**两大能力，并将两者融合：视觉模型把"图像空间"映射到"医学语义空间"（产出疾病名与形态学术语），驱动向量检索命中皮肤科知识库，检索到的资料再反向约束生成措辞，使回答从"自由的视觉描述"收敛为"有据可依的科普"。

**合规与安全定位**：系统仅用于健康科普与初步参考，不构成医疗诊断，不能替代执业医师的面诊与诊断。因此系统内置三层安全防线，并保证风险等级"只上调不下调"、就医提示强制插入。全链路纯本地推理，图片与对话数据不出内网。

### 1.2 项目目标

| 编号 | 目标 | 说明 |
|---|---|---|
| G1 | 图文融合诊断 | 用户上传皮肤照片（可附文字描述），系统输出结构化诊断卡片（观察 / 方向 / 依据 / 留意 / 建议） |
| G2 | 知识库问答 | 用户以纯文字提问，系统基于本地皮肤科知识库检索作答，回答附带依据来源 |
| G3 | 知识库可运营 | 支持文档批量导入、上传、列表管理、检索调试，形成可持续扩充的领域知识资产 |
| G4 | 安全可控 | 三层安全防线（提示词约束 + 结构约束 + 确定性规则兜底），危险信号强制就医提示 |
| G5 | 流式体验 | 文本逐 token 输出，节点级进度提示（"正在分析图像…""正在检索知识库…"） |
| G6 | 高可用与降级 | Ollama 掉线、模型输出脏数据、知识库为空、图片格式非法等异常均有可读的降级结果 |
| G7 | 可部署 | 支持本地多容器部署与云端单容器部署两种形态，模型与数据持久化 |

### 1.3 整体功能需求

系统整体功能需求按"一条主链路 + 四类支撑能力"归纳：

**主链路（核心业务流）**：

```
用户输入（文字 / 图片）
  → 预处理（意图识别与路由）
  → 视觉分析（图片 → 结构化观察，仅图片分支）
  → 查询构建（视觉结论 / 用户问题 → 检索意图）
  → 知识检索（向量召回 + BM25 召回 → RRF 融合 → 可选重排）
  → 回答生成（流式，受检索结果约束）
  → 安全审查（风险等级裁决、免责声明追加、危险信号拦截）
  → 返回用户（SSE 流式 + 结构化卡片）
```

**四类支撑能力**：

1. **接口服务**：chat（对话诊断）、knowledge（知识库管理）、system（健康检查）、users/auth（用户与鉴权）四组 REST API + SSE 流式协议。
2. **知识库运营**：文档解析（含 CJK 文本处理、分块、元数据）、批量导入 CLI、上传接口、列表与检索调试。
3. **模型接入**：本地 Ollama 与云端 OpenAI 兼容 API 双后端开关，视觉模型、文本模型、向量模型统一网关管理。
4. **工程保障**：单元测试（不依赖 Ollama）、静态检查、Makefile 工作流、Docker 多容器 / 单容器两套部署方案。

### 1.4 模块划分思路与依据

模块划分遵循以下四条原则：

1. **按请求链路分层**：系统请求链路为 `API 层 → 智能体编排层 → 服务层 → 数据层`，模块划分首先沿该分层展开，保证每层职责单一、边界清晰。
2. **按变更频率与关注点分离**：智能体编排（业务流程）与模型接入（外部依赖）分开——换模型不动流程；知识库与检索（数据资产）独立成模块——知识运营不干扰代码迭代。
3. **安全独立成模块**：安全审查是横切但强契约的环节（风险只升不降、免责声明幂等追加），涉及合规底线，必须独立模块、独立测试锁定，不允许在业务迭代中被"优化掉"。
4. **前后端按契约解耦**：前端只依赖接口文档（SSE 协议、数据模型、错误码），与后端并行开发。

据此划分出 **八个模块**：

| 模块编号 | 模块名称 | 所属层次 | 核心职责 |
|---|---|---|---|
| M1 | 用户交互前端模块 | 表现层 | 对话界面、图片上传、流式渲染、诊断卡片、知识库管理抽屉 |
| M2 | API 服务与接口层模块 | 接口层 | REST API、SSE 流式协议、请求校验、错误码、静态托管 |
| M3 | 智能体编排核心模块 | 业务编排层 | LangGraph 状态图、意图路由、节点编排、图文融合策略 |
| M4 | 模型接入与网关模块 | 服务层 | Ollama / 云端双后端、视觉分析、结构化输出约束与降级 |
| M5 | 知识库与检索模块 | 服务层 + 数据层 | 文档解析入库、混合检索（向量 + BM25 + RRF）、向量库与元数据存储 |
| M6 | 安全与风控模块 | 横切层 | 22 条确定性安全规则、风险等级裁决、免责声明、用户鉴权 |
| M7 | 测试与质量保障模块 | 工程保障 | 单元测试体系、静态检查、测试环境隔离 |
| M8 | 部署与运维模块 | 工程保障 | Docker 双形态部署、Makefile、运维 CLI、项目文档 |

### 1.5 依赖关系

```
M1 前端 ──依赖(接口契约)──► M2 API 层
M2 API 层 ──依赖─────────► M3 智能体编排 ──依赖──► M4 模型网关
   │                              │                    │
   └──────► M5 知识库检索 ◄───────┘（build_query 驱动）
                 │
M6 安全风控 ◄────┴──（M3/M4/M5 所有出口必须经过）
M7 测试 ──覆盖──► M1~M6 全部模块
M8 部署 ──打包──► 全部模块产物
```

关键约束（模块间的强契约，任何一方不得单方面变更）：

- 视觉分析之后必须经过查询构建才能进入检索，不允许从视觉节点直接跳到生成；
- 闲聊意图可直达生成，检索可被跳过，但**所有出口都必须经过安全审查**；
- 风险等级只上调不下调，免责声明由代码幂等追加、不依赖模型；
- 更换向量模型后必须重建索引（向量维度首次创建时固定）。

## 第二部分 各模块需求详述

### M1 用户交互前端模块

**功能需求**：

1. **对话界面**：支持文字提问与图片上传（拖拽 / 粘贴 / 选择），图片可附补充描述；对话历史展示。
2. **流式渲染**：逐 token 渲染模型输出，同步展示节点级进度提示（"正在分析图像…""正在检索知识库…"），基于 SSE 协议解析事件流。
3. **诊断卡片**：图片识别结果以结构化卡片呈现，含观察、可能方向、依据（知识库来源）、需要留意、建议五个区块。
4. **知识库管理抽屉**：右上角入口，支持文档上传、已入库列表查看、检索测试（不调 LLM 的调试检索）。
5. **异常与降级展示**：后端降级结果（模型离线、知识库为空等）以可读形式提示用户；展示系统免责声明。

**职责边界**：前端只依赖 `docs/接口文档.md` 定义的接口契约（SSE 协议、数据模型、错误码），不感知后端内部实现；不承担任何业务逻辑判断（如风险等级判断一律以后端为准）；开发期通过 `/api` 代理同源访问，不处理跨域。

### M2 API 服务与接口层模块

**功能需求**：

1. **四组 REST API**：chat（对话与诊断，含 SSE 流式端点）、knowledge（文档上传 / 列表 / 检索）、system（健康检查，返回 `ok / degraded` 与修复提示）、users / auth（用户注册登录鉴权）。
2. **请求校验与错误处理**：基于 Pydantic Schema 的入参校验，统一错误码体系，图片格式与大小校验。
3. **SSE 协议实现**：文本增量、节点进度、错误、结束等事件类型的规范下发。
4. **静态托管**：生产模式下托管前端构建产物（挂载顺序必须保证 API 路由优先）。
5. **应用装配**：依赖注入、CORS 配置（逗号分隔解析）、启动预热（Chroma 建集合 + 图编译）。

**职责边界**：API 层只做协议转换、校验与装配，不含业务流程；业务编排在 M3，数据访问在 M5，安全裁决在 M6。接口契约变更须同步更新接口文档并通知前端（M1）。

### M3 智能体编排核心模块（核心模块）

**功能需求**：

1. **状态机定义**：AgentState 全局状态（含路由结果、视觉分析结论、检索意图、检索结果、生成内容、安全审查结论）。
2. **节点实现**：
   - 预处理节点：输入规整、图片合法性初判；
   - 意图路由节点：闲聊 / 纯文字问答 / 图片诊断三路分流（含澄清追问分支）；
   - 视觉分析节点：调用视觉模型产出结构化观察（疾病名、形态学术语）；
   - 查询构建节点：把视觉结论或用户问题转成医学检索意图（图文融合的关键衔接）；
   - 检索节点：调用 M5 检索服务，召回知识片段；
   - 生成节点：流式生成，受检索结果约束；
   - 安全审查节点：调用 M6，做最终裁决与免责声明追加。
3. **编排规则**：视觉分析之后必须经过查询构建才能检索（禁止跳过）；闲聊可直达生成；所有出口必经安全审查。
4. **全局降级策略**：任一节点异常时的可读降级路径设计。
5. **运行器**：图的执行入口，管理流式事件上报。

**职责边界**：本模块是业务中枢，定义"做什么、按什么顺序做"，但"怎么做"委托给 M4（模型调用）、M5（检索）、M6（安全）；不在节点内直接实例化模型客户端（必须走工厂与网关接口）。

### M4 模型接入与网关模块

**功能需求**：

1. **双后端开关**：`SKIN_LLM_BACKEND=ollama|cloud`，本地 Ollama 与云端 OpenAI 兼容 API 可切换，业务层无感知。
2. **模型工厂与网关**：统一封装视觉模型、文本模型、向量模型的调用接口；管理 `keep_alive`、超时、预热。
3. **结构化视觉分析**：通过 JSON Schema 做语法约束输出，三级降级保证任何模型可用（Schema 约束 → 宽松提示 → 正则提取）。
4. **解析容错**：模型输出脏 JSON 时的修复与降级策略。
5. **配置管理**：模型名、端口、路径等集中于配置中心，环境变量前缀 `SKIN_`，路径从项目根推导。

**职责边界**：只负责"把模型调用稳稳地做好"，不涉及业务编排与提示词策略之外的安全

### M5 知识库与检索模块

**功能需求**：

1. **文档处理**：多格式文档解析、CJK 文本处理（空格修复）、智能分块（携带元数据）、jieba 领域词典增强。
2. **入库管道**：CLI 批量导入（`ingest <dir> -c <分类>`）、HTTP 上传入库、重索引命令（`reindex`，换向量模型后必须执行）。
3. **混合检索**：向量召回（跨用词差异）+ BM25 召回（专有名词精确命中）→ RRF 融合 → 可选 LLM 重排；支持不调 LLM 的检索调试命令。
4. **存储层**：Chroma 向量库（PersistentClient）+ SQLite 元数据（文档列表、状态）。
5. **健康检查**：模型就绪检查（`health` 命令），为 system API 提供降级依据。

**职责边界**：知识资产的存储与检索；不决定"何时检索、检索结果如何用于生成"（属 M3）；不做安全过滤（属 M6）。向量库集合维度在首次创建时固定，维度变更必须走重索引流程。

### M6 安全与风控模块

**功能需求**：

1. **确定性安全规则**：22 条规则兜底（危险信号识别：色素痣形态改变、皮损破溃不愈、迅速扩大、伴发热、累及黏膜、呼吸困难等）。
2. **风险等级裁决**：只上调不下调的单调性保证（有单元测试锁定）。
3. **免责声明**：由代码幂等追加，不依赖模型输出（有单元测试锁定）。
4. **就医提示强制插入**：识别到危险信号时强制在回答中插入就医提示。
5. **用户鉴权**：注册 / 登录、会话管理、接口访问控制。

**职责边界**：合规底线的守护者。M3 / M4 / M5 的所有出口结果必须经过本模块；本模块语义变更（规则增删、等级调整）需经队长评审并同步更新测试。

### M7 测试与质量保障模块

**功能需求**：

1. **单元测试体系**：覆盖解析容错、安全不变量（风险单调性、免责声明幂等）、文本处理、RRF 数学性质、意图路由优先级、接口契约（含静态托管顺序回归）；全部用例不依赖 Ollama、秒级跑完。
2. **测试环境隔离**：conftest 在 import 应用之前把 SQLite / Chroma 指向临时目录，避免污染真实数据。
3. **静态检查与格式化**：ruff check / ruff format 工作流。
4. **规范约定**：模型效果评估另建带标注集的流程，不混入单测。

**职责边界**：质量兜底横跨全部模块；各模块的功能测试用例由该模块负责人编写，本模块负责人维护测试体系、夹具与 CI 约定。

### M8 部署与运维模块

**功能需求**：

1. **多容器部署**：docker-compose（API :8000、前端 :8080、Ollama 宿主机）。
2. **单容器云部署**：根目录 Dockerfile + ms_deploy.json + entrypoint（Ollama + API + 前端合并，固定端口 7860，数据持久化卷）。
3. **云端 API 部署**：Dockerfile.cloud，不跑本地模型、对接 OpenAI 兼容云端 API。
4. **Makefile 工作流**：venv / models / ingest / dev / fe-dev / test 一键命令。
5. **项目文档**：系统设计文档、接口文档、部署指南、云端部署文档的维护。

**职责边界**：环境与交付物管理；不修改业务代码；部署配置的变更（端口、挂载、环境变量）须同步文档。

### 3.6 协作机制与里程碑

**协作机制**：

1. **接口先行**：M2 契约由 1 号终审后冻结，M1/M2/M3 并行开发，契约变更须走 1 号裁决；
2. **每日站会（15 分钟）**：同步进度、暴露阻塞，队长现场裁决或会后跟进；
3. **MR 评审**：所有代码经 1 号评审合入；安全相关变更（M6、风险等级、免责声明）必须附测试证明；
4. **联调窗口**：按里程碑由 1 号组织全链路联调，缺陷按"谁的模块谁修，跨模块队长分派"处理。

**里程碑（建议）**：

| 阶段 | 内容 | 里程碑产物 |
|---|---|---|
| 一 · 契约冻结 | 架构与接口设计（1 号主导，全员参与） | 系统设计文档 + 接口文档 v1 |
| 二 · 并行开发 | M1/M2（2 号）、M3/M4/M6（1 号）、M5/M7（3 号） | 各模块可独立运行 + 单测通过 |
| 三 · 集成联调 | 全链路联调（1 号主导，全员参与） | 端到端功能可演示 |
| 四 · 交付部署 | M8 部署验证（3 号主责，1 号审批发布） | 双形态部署可用 + 文档齐备 |
