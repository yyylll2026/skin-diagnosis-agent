# 追问澄清机制（信息完备性判断）

> 在 `route` 之后新增 `check_completeness` 节点：信息不足时先输出结构化追问，
> 而不是拿一句「我脸上起了红疹」去检索出一堆泛泛的资料。

## 一、解决什么问题

用户常抛出信息量极低的一句话。系统原有的行为是硬着头皮检索 + 生成，
结果是回答正确但无用——因为真正决定判断精度的几个维度（多久了、痒不痒、在扩大吗）
根本没被采集。本机制在检索之前插一道**完备性闸门**，把缺失维度问出来。

## 二、四条不可动摇的设计约束

| # | 约束 | 理由 |
|---|------|------|
| 1 | **急症永不追问** | 追问要多花一整轮往返。用户已经说了「迅速增大」「破溃出血」时，多问一句就是延误就医 |
| 2 | **只有个人症状咨询才追问** | 「湿疹怎么护理」追问「长在哪个部位」既荒谬又招人烦 |
| 3 | **图片诊断不追问** | 视觉分析本身产出部位/形态/颜色/分布，信息已较充分；且该接口契约是「返回一次性诊断卡片」 |
| 4 | **追问有上限，用尽即兜底作答** | 「一直被问、始终得不到回答」比「答得不完美」体验更差 |

第 1 条是本机制最重要的安全属性：**安全优先于信息完整**，
与 `safety_service` 的「风险只升不降」是同一价值观的两处体现。

## 三、维度设计

**核心维度**（决定信息是否足够）：

| key | 标签 | 为什么关键 |
|-----|------|-----------|
| `duration` | 出现时间 | 急性与慢性的处置路径完全不同 |
| `location` | 部位与范围 | 部位是最强的先验之一（曝光部位 vs 褶皱部位） |
| `sensation` | 伴随感觉 | 是否瘙痒是重要的鉴别线索 |
| `progression` | 变化趋势 | 变化速度直接关系到是否需要尽快就诊 |

**补充维度**（核心齐了才可能追问，用于把回答做实）：
`trigger` 诱因 / `history` 既往史 / `treatment` 已处理。

抽取全部是**确定性规则**（正则 + 词典），不调模型。理由与安全层一致：
规则可被精确断言，而「问不问」这种分支决策交给模型就变得不可测。

## 四、判定优先级

顺序即优先级，不可随意调整：

```
1. clarify_enabled == False          → 不追问（disabled）
2. 带图                              → 不追问（image）
3. 危险信号（本轮输入 或 累计信息）    → 不追问（urgent），立刻作答并由安全层升级
4. 用户要求直答（「直接回答」「说不清」）→ 不追问（user_skip），转兜底作答
5. 非个人症状咨询（且无待补追问）      → 不追问（knowledge_question）
6. 核心维度命中数 ≥ clarify_min_dimensions → 不追问，正常检索生成
7. 已用轮次 ≥ clarify_max_rounds      → 不追问（round_limit），转兜底作答
8. 其余                              → 追问，轮次 +1
```

第 3 条的扫描对象是**本轮输入 + 累计已收集信息**，
避免上一轮提到的危险信号因为用户换了句话而被漏掉。

## 五、阈值 / 上限 / 兜底

| 配置项 | 默认 | 含义 |
|--------|------|------|
| `SKIN_CLARIFY_ENABLED` | `true` | 总开关 |
| `SKIN_CLARIFY_MIN_DIMENSIONS` | `3` | 核心维度命中 ≥3（最多缺 1 项）就作答 |
| `SKIN_CLARIFY_MAX_ROUNDS` | `2` | 追问轮次上限 |

**兜底的两种触发路径**：

1. **轮次用尽**（`round_limit`）：连续 2 轮追问仍未补齐；
2. **用户要求直答**（`user_skip`）：用户说了「直接回答」「不想说」「说不清」。

两种都转为**带缺口的条件化作答**：`ClarifyService.build_note()` 生成一段提示词注入
知识问答链，要求模型

1. 不假装知道缺失信息，对每个缺失维度给出「如果……则可能……」的条件化分析；
2. 明确说明缺了什么、为什么影响判断，并请用户方便时补充；
3. 结尾给出就医提醒。

## 六、多轮状态管理

**状态存在哪**：SQLite 新增 `clarifications` 表，按 `session_id` 一行。

```sql
CREATE TABLE IF NOT EXISTS clarifications (
    session_id     TEXT PRIMARY KEY,
    collected      TEXT NOT NULL DEFAULT '{}',   -- JSON: {维度 key: 命中片段}
    pending_fields TEXT NOT NULL DEFAULT '[]',   -- JSON: 待补充维度
    rounds         INTEGER NOT NULL DEFAULT 0,
    updated_at     TEXT NOT NULL
);
```

用「一行 JSON」而不是给每个维度加一列：维度集合会随医学设计演进（加一个「既往史」就要加一列），
JSON 让仓储层不必跟着改表。代价是无法按维度检索——但追问状态永远是按 `session_id` 整取的。

**为什么不用 LangGraph 的 checkpointer**：与全项目一致（见 `agent/state.py` 顶部说明）。
图保持无状态、单次请求级；跨轮进度由服务层落库，下一轮再由 API 层读回注入状态。
好处是重启不丢进度，且节点依然不碰数据库、可被独立测试。

**数据的流动**：

```
API 层  clarify.has_pending(session_id)
          └─► build_state(clarify_pending=...)      ← 把「追问未完成」变成普通入参
                └─► route 据此把碎片回复判为「继续咨询」
                      └─► check_completeness 读累计信息、判定、落库
                            └─► case_summary 注入 build_query（提升检索质量）
                            └─► clarify_note  注入 generate（提升回答诚实度）
```

`case_summary` 这一步容易被忽略但很重要：用户补充信息那一轮说的话往往很短
（「三天了，很痒」），单靠这句话检索召回很差，而「部位与范围：面部；出现时间：3 天；
伴随感觉：瘙痒」的信息密度高得多。

## 七、路由的连续性处理

追问后的回复往往是碎片，既不含皮肤关键词也匹配不上寒暄模板。
若不特殊处理，它们会落到 LLM 兜底分类甚至被判成闲聊，
**追问进度就永远推进不到兜底作答**，用户会卡在只被追问、拿不到回答的状态。

因此 `route` 的第 2 个条件加了「或该会话有未完成的追问」：

```python
elif any(keyword in question for keyword in SKIN_KEYWORDS) or state.get("clarify_pending"):
    intent = Intent.KB_QA.value
```

## 八、接口契约变更

| 变更 | 说明 |
|------|------|
| 新增节点 | `check_completeness`（信息完备性判断）、`clarify`（生成追问） |
| 新拓扑 | `route → check_completeness →{clarify→safety_review \| build_query}` |
| 新增 SSE 事件 | `clarify`（判定完成即推送）；`done` 事件同时带一份 `clarify` 做兜底 |
| `ChatResponse` | 新增 `clarify: ClarifyState` 字段 |
| `AgentState` | 新增 `clarify_pending` / `needs_clarification` / `clarify` / `case_summary` / `clarify_note` |
| 前端 | 新增 `ClarifyCard.vue`，渲染「已了解到 / 待补充 / 第 N/M 轮」 |

`clarify` 事件载荷（`ClarifyState`）：

```json
{
  "needs_clarification": true,
  "missing": ["出现时间", "伴随感觉", "变化趋势"],
  "missing_keys": ["duration", "sensation", "progression"],
  "collected": {"部位与范围": "脸"},
  "round": 1,
  "max_rounds": 2,
  "fallback": false,
  "bypassed_reason": ""
}
```

`bypassed_reason` 取值：`urgent` / `image` / `knowledge_question` / `user_skip` / `round_limit` / `disabled`。

## 九、安全性质仍然成立

- **追问内容照常经过 `safety_review`**（`clarify → safety_review` 是图里的边），
  所以免责声明与紧急横幅的保证不依赖节点自觉，而是由拓扑保证；
- **风险等级单调性不受影响**：审查对象仍包含用户输入与视觉结果，追问不引入新的下调路径；
- **急症旁路**保证了追问机制不会成为延误就医的入口。

## 十一、已知取舍与后续方向

- **追问文案用模板而非模型生成**：追问天然是结构化的（缺哪几项决定问哪几句），
  模板更准、零延迟、可断言。若将来要更自然的措辞，可在模板基础上加一层轻量润色，
  但要保留模板作为兜底。
- **轮次上限是硬编码的 2**，不区分「用户积极补充但信息确实多」与「用户在敷衍」。
  若要更聪明，可以按「本轮是否新增了维度」动态放宽。
- **补充维度目前不会单独触发追问**：只在核心维度已齐时才可能被问到，
  避免追问变成一份问卷。
- `error_payload` 会把内部异常细节透传给前端的老问题依旧存在（公网部署前应收紧）。
