# 第 0 章 开始之前：这份代码的"性格"

## 0.1 一句话概括

这是一个**本地化部署的皮肤健康科普系统**：用户上传皮肤照片或提问，系统调用本地 Ollama 上的  
Qwen2.5-VL 做结构化视觉分析，把分析结果转成检索语句去查皮肤科知识库，再把两者融合成一份  
"有据可依"的回答，最后经过一道确定性的安全审查才输出给用户。

规模：后端约 6240 行 Python（`app/` + `scripts/` + `tests/`），前端约 2500 行 Vue。  
79 个单元测试全绿，`ruff` 静态检查通过，测试不依赖 Ollama、秒级跑完。

## 0.2 三条贯穿全局的设计哲学

读懂这三条，你会发现全项目几乎所有"看起来绕"的地方都变得理所当然。

### 哲学一：模型是概率性的，系统必须是确定性的

这是全项目最重要的一条。LLM 的输出不确定，但医疗场景的底线不能不确定。于是代码里反复出现同一  
个模式：**让模型做它擅长的事（理解、生成），把不能出错的事交给确定性代码**。

- 风险等级不能由模型说了算 → `safety_service.py` 用 22 条关键词规则做确定性扫描，取并集后**只升不降**
- 免责声明不能指望模型每次都记得写 → `augment()` 用代码幂等追加
- 意图分类不用模型（要 1~2 秒且可能错）→ `nodes.py` 用关键词规则优先
- 检索 query 生成失败 → `fusion_service.py` 有确定性兜底拼装

### 哲学二：输入是不可信的，输出必须是可解释的

- 用户上传的文件名可能带路径穿越 → `knowledge.py:_safe_filename()` 净化
- 模型吐的 JSON 一定不干净 → `parsing.py` 提供一整套宽容解析
- 用户传 `null` 而不是省略字段 → `schemas/chat.py` 用 validator 归一
- 图片可能是 8MB 的 4000px 原图 → `vision_service.prepare_image()` 先压缩再进模型

### 哲学三：任何单点故障都不能让用户看到白屏

全项目有六处降级路径，每一处都是为了"宁可给一个不完美的回答，也不要空白"：

| 故障点         | 降级行为                           | 代码位置                                |
| ----------- | ------------------------------ | ----------------------------------- |
| Ollama 掉线   | 健康检查仍返回 200，把修复命令写进 `warnings` | `api/v1/system.py:31`               |
| 视觉调用失败      | 转为纯文本问答，错误信息透传前端               | `agent/nodes.py:244`                |
| 模型 JSON 不合法 | 三级 `format` 降级 + 宽容解析          | `services/vision_service.py:178`    |
| 检索失败        | 继续生成，仅附错误前缀                    | `agent/nodes.py:303`                |
| LLM 重排失败    | 静默回退 RRF 原顺序                   | `services/retrieval_service.py:400` |
| token 流缺失   | 用节点产出的整段答案兜底                   | `agent/runner.py:230`               |

# 第 1 章 整体架构

## 1.1 系统要解决的问题与由此产生的技术约束

产品痛点决定了技术选型。理解这一层因果，比记住选了什么更有价值：

| 需求                          | 推导出的技术约束                                |
| --------------------------- | --------------------------------------- |
| 皮肤照片涉及隐私，不能上云               | 必须本地推理 → Ollama + 本地 Chroma             |
| 用户不懂医学术语，不知道该搜什么            | 必须由模型把"图像空间"翻译成"医学语义空间" → 视觉 + 检索**串联** |
| 回答要有依据、不能编造                 | 必须 RAG，且提示词要强制模型只用检索结果                  |
| 医疗场景不能给错的风险判断               | 必须有确定性安全层，且不能被模型的乐观结论覆盖                 |
| 本地 7B 模型上下文有限（默认 2048~4096） | 必须显式抬高 `num_ctx`，并给检索上下文设字符预算           |
| 本地模型响应慢（1~3 分钟/图）           | 必须流式输出 + 节点级进度提示，否则用户以为卡死               |
| 免费云平台只转发单一端口                | 前后端必须能合并到一个容器，静态资源由 FastAPI 托管          |

## 1.3 依赖方向：为什么必须是单向的

这是整个项目最重要的架构纪律。依赖关系严格向下，**绝不向上**：

```
main.py  →  api/  →  agent/  →  services/  →  repositories/  →  core/ + config
```

为什么这条规则不能破？看 `main.py` 的设计意图：

> `main.py` 只负责「组装与横切关注点」（日志、CORS、异常、生命周期），业务逻辑一律下沉到  
> `api/v1` → `agent` → `services`。这样 `main.py` 在任何时候都只有几十行，新人接手时一眼能看清系统有哪些横切能力。  
> —— `app/main.py:1-5`

具体收益：

1. **可测试性**。`tests/test_agent_routing.py` 里有一行很说明问题的代码：
   ```python
   def _route_nodes() -> AgentNodes:
       """构造一个不注入任何 service 的实例——路由逻辑不依赖它们。"""
       return AgentNodes.__new__(AgentNodes)
   ```
   用 `__new__` 绕过 `__init__`，直接测试 `route()` 方法。**如果节点里混了数据库访问或 HTTP 调用，  
   这个测试根本写不出来。** 这就是分层的兑现方式。
2. **可替换性**。`repositories/vector_store.py` 换成 Milvus，服务层不用改；  
   `llm_factory.py` 换 embedding 后端，业务代码零改动。
3. **可定位性**。响应慢？先看 `X-Elapsed-Ms` 响应头，再看 `state["timings"]`  
   （每个节点都记了耗时，见 `nodes.py:_elapsed`），直接定位到节点。

**反过来检验**：如果你发现自己在 `core/parsing.py` 里 `import app.services`，那就是设计被破坏了。

## 1.4 一次带图请求的完整生命周期

以"用户上传照片 + 写了句补充说明"为例，完整走一遍（这是理解全项目的黄金路径）：

```
① 浏览器
   ChatPanel.send()  →  push 用户消息 + 占位的 assistant 消息（status='loading'）
                     →  streamAgentChat({session_id, message, image_base64, image_mime})
                     →  fetch POST /api/v1/agent/chat（Accept: text/event-stream）

② 接口层  chat.py:agent_chat
   - session_id 为空则生成 s-xxxxxxxxxxxx
   - store.ensure_session() 建会话
   - store.add_message(role='user')  ← 注意：先落库，再读历史
   - _load_history() 从元数据库读最近 6 轮
   - AgentRunner.build_state() 组装初始状态
   - payload.stream=True → 返回 EventSourceResponse

③ 编排层  AgentRunner.astream_events
   先 yield 一个 meta 事件（告诉前端有哪些节点、要不要检索）
   然后开始消费 LangGraph 的事件流

④ LangGraph 依次执行 7 个节点
   preprocess       base64 解码 → EXIF 校正 → 缩到 1280px → 重编码 JPEG
   route            有图 → intent = image_diagnosis
   vision_analyze   调 Qwen2.5-VL，format 传 JSON Schema，拿到结构化诊断
   build_query      视觉结果 → 3 条医学术语检索语句（← 融合的落点）
   retrieve         向量召回 + BM25 召回 → RRF 融合 → 取 top 4 → 拼上下文
   generate         融合链生成自然语言回答（流式吐 token）
   safety_review    规则扫描 → 追加免责声明 / 紧急横幅

⑤ 事件流回传（8 种事件，见 2.6.4）
   node(running/done) → vision → sources → token×N → done

⑥ 前端按事件更新 UI
   onNode   → 更新"正在分析图像…"进度
   onVision → 渲染 DiagnosisCard
   onSources→ 渲染 SourceList
   onToken  → 逐字追加到气泡
   onDone   → status='done'，写入 localStorage
```

**关键观察**：接口层和编排层之间传递的是一个**普通 dict**（不是对象、不是 DTO）。这是刻意的——  
LangGraph 的状态就是 dict，中间加一层转换只会增加噪音。类型的保障由 `AgentState`（TypedDict）  
在静态检查层面提供，运行时由 `schemas/` 在**边界**（用户输入、模型输出）提供。

## 1.5 控制流：LangGraph 如何"合并"状态

这是初学者最容易困惑的点。看 `nodes.py` 的返回：

```python
def route(self, state: AgentState) -> dict[str, Any]:
    ...
    return {"intent": intent, "timings": _elapsed(state.get("timings") or {}, "route", started)}
```

节点**只返回自己产生的字段**，不返回整个 state。LangGraph 负责把它们合并进全局状态。

由此推出三条实践规律：

1. **每个节点都要显式读取上游字段**（`state.get("queries")`），因为你的输入来自共享状态，不是函数参数。
2. **列表类字段要手动累积**。看 `nodes.py` 里错误的传递：
   ```python
   errors = list(state.get("errors") or [])
   ...
   return {"vision": None, "errors": [*errors, message], ...}
   ```
   TypedDict 没有 reducer（除非用 `Annotated[list, operator.add]`），所以新错误必须自己拼接旧错误，  
   否则会被整体覆盖。这是**真实的坑**：如果你在 `preprocess` 里写 `{"errors": [msg]}`，  
   前面节点记录的错误就丢了。
3. **`total=False` 的意义**（`state.py:23`）：所有字段可选，因为不同分支只填自己负责的部分。  
   纯文本问答不会填 `vision`，图片诊断也不会填空的 `queries`。

**为什么不用 LangGraph 的 checkpointer 存会话？** `state.py` 顶部给了三条理由：

> 1. **可查询**：前端要「会话列表 + 历史回放」，需要能按 session_id 查、能删；  
>    checkpointer 的存储格式是框架内部实现，不适合直接当业务表用
> 2. **可控**：图片是多模态输入的大对象，塞进 checkpoint 会让存储快速膨胀
> 3. **可移植**：换 LangGraph 版本时不必担心 checkpoint 兼容性

所以状态是**单次请求级**的：API 层从元数据库读出最近 N 轮历史注入 `history`，跑完即弃。  
这是一个典型的"**框架提供了能力，但业务约束决定了不该用**"的判断。

## 1.6 数据流：三类数据的不同归宿

理解这个分类，你就不会问"会话历史为什么不在 Chroma 里"：

| 数据       | 归宿                               | 为什么                          |
| -------- | -------------------------------- | ---------------------------- |
| 知识库文档向量  | Chroma                           | 需要相似度检索                      |
| 知识库文档元数据 | 元数据库 `documents` 表             | 需要列表、删除、按 doc_id 查           |
| 会话与消息    | 元数据库 `sessions` / `messages` 表 | 需要按 session_id 查、需要可删、需要前端列表 |
| 上传的原始文件  | `data/uploads/`                  | 与人工语料分目录，删除时不会误伤             |
| 投喂的语料    | `data/docs/`                     | 人工维护，删除文档只移出索引、不删原文件         |
| 图片字节     | **不持久化**                         | 只在单次请求内使用；历史里用占位符保留语义        |

> 「元数据库」= SQLite（默认，`data/app.db`）或 PostgreSQL（设 `SKIN_DATABASE_URL`）。

最后一行体现了一个重要取舍。`chat.py:_load_history` 里：

```python
text = (
    f"[用户上传了一张皮肤照片] {content}".strip()
    if row.get("has_image")
    else content
)
```

历史里不重放图片（体积大且无必要），但**保留"当时有图"这个事实**，让模型知道上下文。  
仅存一个 `has_image` 布尔位就够——这是"存最少的信息，保留最大的语义"。

## 2.1 配置层 `app/config.py`（194 行）

配置是唯一真相源。这个文件短，但藏着三个值得学的技巧。

### 技巧一：用 `env_prefix` 做命名空间隔离

```python
model_config = SettingsConfigDict(
    env_file=BACKEND_DIR / ".env",
    env_file_encoding="utf-8",
    env_prefix="SKIN_",
    extra="ignore",
    case_sensitive=False,
)
```

`env_prefix="SKIN_"` 意味着字段 `ollama_base_url` 对应环境变量 `SKIN_OLLAMA_BASE_URL`。

**为什么重要**：本机可能同时跑着别的服务，如果直接用 `OLLAMA_BASE_URL`，两个项目的配置会串味。  
`extra="ignore"` 则让 `.env` 里多出的变量不报错——这在团队协作（各人 `.env` 进度不同）时很关键。

### 技巧二：`NoDecode` —— 一个必须理解的坑

```python
cors_origins: Annotated[list[str], NoDecode] = Field(
    default_factory=lambda: ["http://localhost:5173", "http://127.0.0.1:5173"]
)

@field_validator("cors_origins", mode="before")
@classmethod
def _split_origins(cls, v: object) -> object:
    """允许用逗号分隔的字符串书写 CORS 白名单。"""
    if isinstance(v, str):
        return [item.strip() for item in v.split(",") if item.strip()]
    return v
```

代码注释本身就是最好的教材：

> **注意 NoDecode**：pydantic-settings v2 默认会把 list/dict 字段当 JSON 解析，而这里希望支持  
> `a,b,c` 这种更符合运维直觉的逗号分隔写法。**不加 NoDecode 的话，逗号串会在进入 validator 之前  
> 就先抛 SettingsError。**  
> —— `app/config.py:38-40`

这里揭示了一个通用规律：**pydantic 的解析顺序是「类型解码 → validator」**。  
`mode="before"` 只保证在**校验**之前，不保证在**解码**之前。要拦截解码，必须先用 `NoDecode` 关掉它。

### 技巧三：`computed_field` 派生路径 + validator 防御

```python
@field_validator("chroma_dir", "sqlite_path", "data_root", "web_dir", mode="before")
@classmethod
def _empty_path_is_none(cls, v: object) -> object:
    """`.env` 里写成空字符串时按未配置处理，回落到默认 data 目录。

    否则 pydantic 会把 `SKIN_SQLITE_PATH=` 解析成 `Path('.')`，
    sqlite 无法打开当前目录，健康检查直接 500。
    """
    if v is None:
        return None
    if isinstance(v, str) and not v.strip():
        return None
    return v
```

**这段 validator 是后补的修复**，对应一次真实故障：`backend/.env` 里写了 `SKIN_SQLITE_PATH=`（空值），  
pydantic 把空字符串解析成 `Path('.')`，于是 `sqlite3.connect('.')` 报  
`OperationalError: unable to open database file`，健康检查 500。

> 💡 **学习点**：`.env` 模板里写 `KEY=` 这种空占位是很常见的习惯。  
> 但如果字段类型是 `Path`，空字符串不等于"未配置"，而等于"当前目录"。  
> 这类 bug 的排查路径是：看堆栈 → 发现是路径问题 → 检查配置来源 → 意识到 `.env` 覆盖了默认值。
>
> ⚠️ **注意**：这个修复目前仍在工作区未提交（`git status` 显示 `M backend/app/config.py`），  
> 建议提交并补一条回归测试锁住「空串 → 回落默认路径」的行为。

## 2.2 契约层 `app/schemas/`（375 行）

### 核心认知：Pydantic 模型承担双重职责

`schemas/diagnosis.py` 开头写得很清楚：

> 这些 Pydantic 模型承担两个职责：
>
> 1. **约束 LLM 输出**：模型 JSON Schema 会被注入提示词，让 Qwen2.5-VL 按结构吐 JSON；返回后再用同一套模型校验
> 2. **约束前后端契约**：FastAPI 的响应模型，前端 `DiagnosisCard.vue` 严格按此渲染

**这是一个非常经济的复用**：同一份类型定义，既是"给模型看的输出规范"，又是"给前端看的接口文档"，  
还是"运行时校验的规则"。三者永远不会漂移。

### 设计原则：所有字段都给默认值

```python
class VisionDiagnosis(BaseModel):
    summary: str = Field(default="", description="一句话视觉印象总述")
    image_quality: str = Field(default="", description="图像质量评价：是否清晰/过暗/过曝/非皮肤")
    observations: LesionObservation = Field(default_factory=LesionObservation)
    hypotheses: list[DiagnosisHypothesis] = Field(default_factory=list)
    risk_level: RiskLevel = RiskLevel.LOW
    ...
```

理由（`diagnosis.py:8-9`）：

> 所有字段都给默认值，是因为本地小模型的 JSON 输出经常缺字段——  
> **宁可让缺失字段回落到「未描述」，也不要因为一个字段校验失败丢掉整次诊断。**

这是"宽容"哲学在类型层面的体现。注意 `list` 字段必须用 `default_factory` 而非 `default=[]`——  
后者是 Python 经典的共享可变默认值陷阱。

### 技巧：`field_validator(mode="before")` 做输入归一

模型输出的"不干净"有三种典型形态，代码逐个应对。

**形态 1：枚举值写中文**

```python
_RISK_ALIASES: dict[str, str] = {
    "low": "low", "低": "low", "低风险": "low", "轻微": "low", "无需处理": "low",
    "medium": "medium", "中": "medium", "中等": "medium", "中度": "medium", "一般": "medium",
    "high": "high", "高": "high", "较高": "high", "高风险": "high", "严重": "high",
    "urgent": "urgent", "紧急": "urgent", "危急": "urgent", "急诊": "urgent", "立即就医": "urgent",
}

class RiskLevel(StrEnum):
    @classmethod
    def from_any(cls, value: object) -> RiskLevel:
        if isinstance(value, RiskLevel):
            return value
        key = str(value or "").strip().lower()
        return cls(_RISK_ALIASES.get(key, "medium"))
```

注意兜底值是 `medium` 而不是 `low`——**无法识别时宁可保守**。这和安全层的"只升不降"是同一个价值观。

**形态 2：数值范围不对**

```python
@field_validator("confidence", mode="before")
@classmethod
def _normalize_confidence(cls, v: object) -> object:
    """模型常把置信度写成百分数（如 75），统一归一到 0~1。"""
    try:
        value = float(v)
    except (TypeError, ValueError):
        return 0.5
    if value > 1.0:
        value = value / 100.0
    return max(0.0, min(1.0, value))
```

**形态 3：结构写成字符串**

```python
@field_validator("hypotheses", mode="before")
@classmethod
def _ensure_hypotheses(cls, v: object) -> object:
    """把 hypotheses 的三种「非规范但常见」写法收敛成对象数组。"""
    if isinstance(v, str):
        return [{"name": item.strip()} for item in v.replace("，", "、").split("、") if item.strip()]
    if isinstance(v, dict):
        return [v]
    if isinstance(v, list):
        return [{"name": item.strip()} if isinstance(item, str) else item for item in v]
    return v
```

注释点出了关键：

> 模型实际会输出：纯字符串、顿号分隔的字符串、字符串数组、单对象。  
> **少处理一种就会导致整条 hypotheses 被校验丢弃（置信度信息全丢）**，因此这里逐一覆盖。

> 💡 **学习点**：这类 validator 的正确写法是"列出所有实际观测到的形态"，而不是"写出理想形态然后  
> 靠 except 兜住"。前者的依据是真实日志，后者是想象。

### 前端契约的"容忍显式 null"

`schemas/chat.py` 有一段很值得读的注释（`chat.py:37-46`）：

> 踩过的坑：前端在没有图片时会序列化成 `"image_mime": null`  
> （JS 里 `obj.field ?? null` 是最自然的写法），而后端的默认值  
> 只在字段**缺失**时生效，显式传 null 会被判为类型错误并返回 400。
>
> 这不是前端的错——**「可选字段带默认值」的语义就应当包含「传 null 等于没传」**。  
> 因此在这里统一把 null 归一到默认值，前端可以放心地不做字段裁剪。

对应的实现是三个 before-validator。**这个决策的方向很值得学**：bug 出现在前端（多传了 null），  
但修复放在后端（容忍 null）。理由不是"后端好欺负"，而是**契约语义上就该如此**。  
判断"该改哪一边"的依据是语义合理性，不是谁改起来方便。  
`tests/test_schemas.py` 里有 6 条测试专门锁这个行为（如 `test_all_optional_fields_explicitly_null_is_accepted`）。

### `StrEnum` 的一个易错点

`Intent`、`RiskLevel`、`DocCategory` 都用 `StrEnum`（Python 3.11+ 特性），  
**继承 str 又保持枚举语义**，序列化时直接是字符串。  
如果你用普通 `Enum`，JSON 里会出现 `<RiskLevel.LOW: 'low'>` 这类不可读的东西。  
两条测试专门验证：`test_intent_serializes_as_plain_string`、`test_risk_level_serializes_as_plain_string`。

### 2.3.1 `errors.py` —— 异常体系的设计

```python
class AppError(Exception):
    """业务异常基类。``code`` 供前端做分支处理，``message`` 直接面向用户展示。"""

    code = "internal_error"
    http_status = 500

    def __init__(self, message: str, detail: Any = None) -> None:
        super().__init__(message)
        self.message = message
        self.detail = detail


class OllamaUnavailableError(AppError):
    code = "ollama_unavailable"
    http_status = 503

class ModelOutputError(AppError):
    code = "model_output_invalid"
    http_status = 502

class ImageValidationError(AppError):
    code = "image_invalid"
    http_status = 400
```

三个设计决策：

1. **扁平继承**：所有业务异常直接继承 `AppError`，不搞多层继承树。注释说"刻意保持扁平"。  
   业务异常数量少（5 个），多一层抽象只增加跳转成本。
2. **`code` 和 `http_status` 是类属性**，不是实例属性。异常本身携带"如何翻译成 HTTP 响应"的信息，  
   于是 `main.py` 的处理器只需一行：
   ```python
   @app.exception_handler(AppError)
   async def handle_app_error(request: Request, exc: AppError) -> JSONResponse:
       return JSONResponse(status_code=exc.http_status, content=error_payload(exc))
   ```
3. **`message` 面向用户，`detail` 面向开发者**：
   ```python
   def error_payload(exc: BaseException) -> dict[str, Any]:
       if isinstance(exc, AppError):
           return {"code": exc.code, "message": exc.message, "detail": exc.detail}
       return {"code": "internal_error", "message": f"服务器内部错误：{exc}", "detail": None}
   ```
   注意兜底分支**把非业务异常的内部信息也塞进了 message**，而 `runner.py` 会把它通过 SSE 透传给前端。  
   严格来说这在生产环境会泄露内部细节，是可以用 `debug` 开关收紧的地方——留作思考题。

`setup_logging` 用全局标志实现幂等：

```python
        return
    ...
```

### 2.3.2 `parsing.py` —— 全项目鲁棒性的基石 ⭐

**这是我认为最值得精读的 194 行代码。** 它解决的问题是：本地小模型的 JSON 输出永远不干净。

> 本地小模型的 JSON 输出经常「不那么干净」：带 markdown 围栏、带解释性前言、  
> Python 风格的 True/None、尾随逗号。直接 `json.loads` 必然频繁失败。

#### 第一层：剥围栏与配平扫描

````python
_FENCE_RE = re.compile(r"```(?:json|JSON)?\s*(.*?)```", re.DOTALL)

def _strip_fences(text: str) -> str:
    """去掉 markdown 代码围栏，保留围栏内内容。"""
    match = _FENCE_RE.search(text)
    return match.group(1).strip() if match else text.strip()
````

更精彩的是配平扫描：

```python
def _find_balanced_span(text: str, opener: str, closer: str) -> str | None:
    """从第一个 ``opener`` 开始，扫描出配平的括号区间。

    用状态机跳过字符串内部的括号，避免 ``{"desc": "含 } 的文本"}`` 被误截断。
    """
    start = text.find(opener)
    if start < 0:
        return None
    depth = 0
    in_string = False
    escaped = False
    for idx in range(start, len(text)):
        char = text[idx]
        if in_string:
            if escaped:
                escaped = False
            elif char == "\\":
                escaped = True
            elif char == '"':
                in_string = False
            continue
        if char == '"':
            in_string = True
        elif char == opener:
            depth += 1
        elif char == closer:
            depth -= 1
            if depth == 0:
                return text[start : idx + 1]
    return None
```

**它在做什么**：模型输出可能是 `好的，分析结果如下：{"summary": "含 } 符号的描述", ...}`。  
如果用正则或 `rfind('}')` 提取，字符串里的 `}` 会把区间截错。  
这个状态机维护三个状态（`depth` / `in_string` / `escaped`），正确处理转义。

> 💡 **学习点**：这是"手写词法扫描器"的最小范例。三状态机（深度、是否在字符串内、是否转义）  
> 是解析结构化文本的标准套路，从 JSON 提取到模板引擎都通用。注意 `escaped` 的处理顺序——  
> 先判断转义，再判断引号，否则 `\"` 会被误认为字符串结束。

#### 第二层：语法修补

```python
_PY_LITERAL_MAP = {"True": "true", "False": "false", "None": "null"}

def _repair(raw: str) -> str:
    """修补常见 JSON 语法瑕疵。"""
    fixed = raw
    # 去掉尾随逗号：{"a": 1,} / [1,2,]
    fixed = re.sub(r",\s*([}\]])", r"\1", fixed)
    # Python 风格字面量
    for key, value in _PY_LITERAL_MAP.items():
        fixed = re.sub(rf"\b{key}\b", value, fixed)
    return fixed
```

模型（尤其经 Python 语料训练的）常把 `true` 写成 `True`。`\b` 边界保证不会误伤 `TrueStory` 这类词。

#### 第三层：多候选依次尝试 ⭐

```python
def extract_json(text: str, expect: str = "object") -> Any:
    opener, closer = ("{", "}") if expect == "object" else ("[", "]")
    cleaned = _strip_fences(text)

    # 依次尝试：原文 -> 配平子串 -> 修补后的配平子串
    candidates: list[str] = [cleaned]
    span = _find_balanced_span(cleaned, opener, closer)
    if span:
        candidates.extend([span, _repair(span)])
    candidates.append(_repair(cleaned))

    for candidate in candidates:
        try:
            return json.loads(candidate)
        except json.JSONDecodeError:
            continue

    logger.warning("JSON 提取失败，原文前 300 字：{}", text[:300])
    raise ValueError("无法从模型输出中解析出 JSON")
```

**这是"策略序列"模式**：从最保守到最激进依次尝试，第一个成功即返回。  
注意顺序——先试原文（不破坏原始内容），再试配平（可能截断但范围准确），最后试修补。  
`logger.warning` 记录原文前 300 字，是**为失败留证据**：模型换了、提示词改了，  
你能从日志看出为什么解析不了。

#### 第四层：`parse_model` 的逐字段回退

```python
def parse_model(text: str, model_cls: type[T]) -> T:
    data = extract_json(text, expect="object")
    if not isinstance(data, dict):
        raise ValueError(f"期望 JSON 对象，实际得到 {type(data).__name__}")

    allowed = set(model_cls.model_fields.keys())
    filtered = {k: v for k, v in data.items() if k in allowed}   # 丢未知键
    try:
        return model_cls.model_validate(filtered)
    except ValidationError as exc:
        logger.warning("模型输出校验失败，尝试宽松回退：{}", exc.errors()[:3])
        # 逐字段回退：保留能校验通过的字段，其余走默认值
        safe: dict[str, Any] = {}
        for key, value in filtered.items():
            try:
                model_cls.model_validate({**{k: None for k in allowed}, key: value})
                safe[key] = value
            except ValidationError:
                continue
        try:
            return model_cls.model_validate(safe)
        except ValidationError as exc2:
            raise ValueError(f"模型输出不符合约定结构：{exc2.errors()[:3]}") from exc2
```

**逐字段回退的逻辑**：整体校验失败时，**一次校验一个字段**——把其他字段填成 `None`（触发默认值），  
只保留当前字段的值。这样能精确找出"哪个字段有问题"，把它丢掉，保留其余全部信息。

> 💡 **学习点**：这是"**部分成功的降级**"模式。对比朴素做法——整体 `try/except` 然后返回默认对象——  
> 那会丢掉所有字段。这里做到的是"尽可能多地保住信息"。代价是 O(n) 次校验，  
> 但 n 只有不到 10 个字段，可以接受。**这类"用可接受的性能代价换取信息保全"的权衡，在数据管道里非常常见。**

#### 第五层：`inline_json_schema` 展开 `$ref`

```python
def inline_json_schema(schema: dict[str, Any]) -> dict[str, Any]:
    """把 JSON Schema 里的 ``$ref`` 就地展开。

    为什么必须做这一步：``model_json_schema()`` 会把嵌套模型抽到 ``$defs`` 里，
    再用 ``{"$ref": "#/$defs/LesionObservation"}`` 引用。Ollama 的 ``format``
    参数背后是 GBNF 语法编译器，对 ``$ref`` 的支持在不同版本间并不一致，
    展开成自包含的扁平结构是兼容性最好的写法。
    """
    defs = schema.pop("$defs", {})

    def resolve(node: Any, depth: int = 0) -> Any:
        if depth > 12:  # 防御性上限，避免异常 schema 导致栈溢出
            return node
        if isinstance(node, dict):
            if "$ref" in node:
                ref_name = str(node["$ref"]).rsplit("/", 1)[-1]
                target = defs.get(ref_name, {})
                siblings = {k: v for k, v in node.items() if k != "$ref"}
                return resolve({**target, **siblings}, depth + 1)
            return {key: resolve(value, depth + 1) for key, value in node.items()}
        if isinstance(node, list):
            return [resolve(item, depth + 1) for item in node]
        return node

    resolved = resolve(schema)
    return resolved if isinstance(resolved, dict) else schema
```

三个细节：

- `schema.pop("$defs", {})` —— 原地修改并移除 `$defs`，避免展开后残留无用定义
- `depth > 12` —— **防御性上限**。递归展开理论上可能无限循环（互相引用的 schema），加个上限
- `siblings` —— JSON Schema 允许 `$ref` 和兄弟键共存，合并时兄弟键覆盖目标

测试：`test_inline_json_schema_removes_refs`。

### 2.4.1 `db.py` + `database.py` —— SQLAlchemy Core，不用 ORM

> 职责边界刻意收窄：**只存结构化元数据与对话历史**，不存向量。
> 访问层用 **SQLAlchemy Core**（不是 ORM）：仓储层保留全部显式 SQL，
> 只借 SQLAlchemy 的连接与参数绑定，让同一份语句既能跑 SQLite 也能跑 PostgreSQL。

**为什么从「纯 `sqlite3`」改成 SQLAlchemy Core**：

最初确实是标准库 `sqlite3` + 手写 SQL（省依赖）。但一旦要支持 PostgreSQL，
纯 `sqlite3` 就锁死了方言。换成 Core 后语句仍然手写，只多了「连接 + 绑定」这一层薄封装，
却换来跨方言能力。**没有选完整 ORM**——十几个简单语句不值得引入映射与懒加载的心智负担。

**两个模块的分工**：

| 文件 | 职责 |
|------|------|
| `database.py` | `Database` 连接封装、URL 归一化、`?` 占位符改写、方言分支函数、`run_migrations()` |
| `db.py` | `MetadataStore`：业务仓储，全部显式 SQL + 一句一句的方法 |

`MetadataStore.__init__(self, target: Path | str)` 现在做两件事：

```python
def __init__(self, target: Path | str) -> None:
    self._db = Database(normalize_database_url(target))
    self._db.ensure_schema()   # 交给 Alembic，运行时零 DDL
```

**方言适配的三处坑**（`database.py`）：

1. **占位符**：仓储层继续写 `?`，由 `translate_placeholders()` 改写成 `:p0/:p1`，
   再交给 SQLAlchemy 按目标方言翻译。**关键是不能用正则**——`WHERE note = '?'`
   和 `'it''s ?'` 里的问号不是占位符，所以用了一个**识别字符串字面量的字符扫描器**：

   ```python
   def translate_placeholders(sql: str) -> str:
       """把 ? 占位符改写成 :p0/:p1；跳过字符串字面量里的 ?。"""
       out, idx, i, quote = [], 0, 0, None
       while i < len(sql):
           ch = sql[i]
           if quote:                      # 在字符串字面量内
               if ch == quote:
                   if i + 1 < len(sql) and sql[i + 1] == quote:  # '' 转义
                       out.append(ch * 2); i += 2; continue
                   quote = None
               out.append(ch)
           elif ch in ("'", '"'):
               quote = ch; out.append(ch)
           elif ch == "?":
               out.append(f":p{idx}"); idx += 1
           else:
               out.append(ch)
           i += 1
       return "".join(out)
   ```

2. **`MIN(a, b)`**：SQLite 支持多参 `MIN`（逐元素取小），PostgreSQL 没有这个重载；
   统一走 `dialect_min_expression(column, ceiling, *, is_sqlite)` → PostgreSQL 用 `LEAST(a, b)`。

3. **`LIKE`**：SQLite 的 `LIKE` 对 ASCII 已大小写不敏感，PostgreSQL 必须显式 `ILIKE`；
   走 `dialect_like_operator(*, is_sqlite)`。

**`QueryResult` 的取值时机**（一个容易踩的坑）：

仓储层有多处「`with` 块内 `execute`、出块后读 `rowcount`」的写法，而连接一旦出块就归还连接池。
所以 `QueryResult` **在构造时就把结果集与 `rowcount` 全部取完**，调用方无论怎么写都不会踩到
「连接已归还、游标失效」。这是「先取完再交出去」比「惰性游标」更安全的一个反直觉结论。

**建表：Alembic 是 schema 的唯一来源**

运行时不再执行任何 DDL。`ensure_schema()` 调用 `run_migrations(url)`，后者**程序式构造
`Config()`**（不读 `alembic.ini`，因为 Alembic 用 `encoding="locale"` 读 ini，中文注释会在
GBK 环境直接崩）。老 SQLite 库的「补列」逻辑也搬进了 `0001_initial_schema.py`
（且 `ALTER` 必须排在建 `idx_sessions_user` 之前）。

**`safe_url` 不用 `render_as_string`**：SQLAlchemy 的 `URL.render_as_string()` 会把
Windows 路径里的 `:` 编码成 `%3A`（`sqlite:///C%3A/...`），日志里看着像坏掉了。
所以手工拼接连接串。

**幂等写入仍用 SQL**：`INSERT ... ON CONFLICT(doc_id) DO UPDATE SET ...`。

> ⚠️ **注意一个细节**：`DO UPDATE SET` 里**没有 `source`**。意味着重新上传同名文档时，
> `source` 保持旧值（实测确认，见 4.3 节）。

**历史消息的取法** —— 一个经典的 SQL 陷阱（跨方言后依然成立）：

```python
def list_messages(self, session_id: str, limit: int = 100) -> list[dict[str, Any]]:
    """按时间正序取出会话消息（用于历史回放与上下文拼装）。"""
    rows = self._db.execute(
        """
        SELECT role, content, has_image, created_at FROM messages
        WHERE session_id = ? ORDER BY id DESC LIMIT ?
        """,
        (session_id, limit),
    )
    return list(reversed(rows.all()))
```

**注意 `ORDER BY id DESC LIMIT ?` 然后 `reversed()`**。为什么不直接 `ORDER BY id ASC LIMIT ?`？

因为 SQL 的 `LIMIT` 是在排序后取**前 N 条**。如果按 ASC 取前 N 条，你拿到的是**最早的** N 条；
而需求是"**最近的** N 条，按时间正序排列"。所以必须 DESC 取最近 N 条，再反转成正序。
**这是一个非常经典的陷阱**，反复出现在"取最近 N 条记录"的场景里。

> 换库冒烟测试：`tests/repository_workout.py` 会调用 `MetadataStore` 的**每一个公开方法**，
> 既是 SQL 覆盖率的守门人，也是「换库后有没有哪条语句跑不通」的冒烟测试。

### 2.5.1 `ollama_client.py` —— 为什么要绕过 LangChain

> 为什么不完全依赖 LangChain 的 ChatOllama？
>
> - **结构化输出**：Ollama ≥0.5 支持 `format` 传 JSON Schema 做语法约束，这是把「模型自由文本」  
>   变成「可校验对象」最可靠的手段，而 LangChain 的封装未暴露该参数
> - **健康检查 / 模型列举**：需要直接打 `/api/tags`
> - **版本兼容**：LangChain 对 Ollama 多模态消息的处理在 0.2/0.3 之间有差异
>
> 本模块只做「协议适配」，不含任何业务语义。

**"不含任何业务语义"这句话是模块的自我约束**，也是它易测试的原因——只做 HTTP 请求与响应形状转换。

图片挂载的实现：


图片必须附在**最后一条 user 消息**上（Ollama API 约定）。  
**这类 API 细节正是"直连 REST"的价值：你完全知道发生了什么，不会被框架的抽象藏起来。**

错误到异常的映射：

```python

except httpx.HTTPError as exc:
```

两个细节：

1. **`from exc` 保留异常链**。traceback 能同时显示"原始错误"和"转换后的错误"，排查时不丢底层信息。
2. **错误消息是行动指南**。`"请确认服务已启动：ollama serve"` 比 `"Connection refused"` 好得多。

超时按用途区分（连接 5s / 读 180~~300s / 写 30~~60s / 池 10s），**视觉超时明显大于文本超时**  
（`vision_service` 传 `settings.vision_timeout = 300`），因为 7B 模型在 CPU 上单张图要 1~3 分钟。

**`lru_cache(maxsize=8)` 的 8 不是随便写的**：参数组合只有"3 个模型 × 2~3 个温度"这几种，  
留 8 个位置足够覆盖且不会无限增长。用函数参数做缓存键，等于  
**用"参数相同 = 实例相同"实现去重**，比手写 `if model not in self._cache` 优雅。

模块文档的第一条理由最实际：

> **连接复用**：ChatOllama 内部持有 httpx 客户端，反复 new 会耗尽连接

工厂模式的第二个收益是**可替换性**，在 embedding 上体现得最清楚：

```python
def _build_embeddings(settings: Settings) -> Embeddings:
    backend = settings.embedding_backend

    if backend == "ollama":
        return OllamaEmbeddings(model=settings.embedding_model, base_url=settings.ollama_api, ...)

    from chromadb.utils import embedding_functions   # 延迟导入

    if backend == "hf":
        try:
            fn = embedding_functions.SentenceTransformerEmbeddingFunction(
                model_name=settings.embedding_hf_model
            )
        except Exception as exc:
            raise EmbeddingError(
                "加载本地 sentence-transformers 模型失败，请先安装可选依赖：pip install -e \".[hf]\"",
                str(exc),
            ) from exc
        return _ChromaEFAdapter(fn)

    return _ChromaEFAdapter(embedding_functions.DefaultEmbeddingFunction())
```

三个后端都返回统一的 `Embeddings` 接口，业务代码完全不知道用了哪个。这就是**适配器模式**：

```python
class _ChromaEFAdapter(Embeddings):
    """把 Chroma 的 EmbeddingFunction 适配成 LangChain 的 Embeddings 接口。"""

    def __init__(self, fn: Any) -> None:
        self._fn = fn

    def embed_documents(self, texts: list[str]) -> list[list[float]]:
        return [[float(x) for x in vec] for vec in self._fn(texts)]

    def embed_query(self, text: str) -> list[float]:
        return self.embed_documents([text])[0]
```

**这个 12 行的类是整个"可替换 embedding"能力的支点。** Chroma 的 `EmbeddingFunction` 是个可调用对象，  
LangChain 要求 `embed_documents` / `embed_query` 两个方法，中间的桥就是它。  
注意 `float(x)` 强制转换——Chroma 可能返回 numpy float32，直接传递或序列化会出问题。

`from chromadb.utils import embedding_functions` 是**延迟导入**，注释说明理由：  
"只有真正用到时才需要 chromadb 的额外依赖"。默认走 Ollama 时，这条 import 永不执行。

> 💡 **学习点**：延迟导入（函数内 import）常被视为坏味道，但在**可选的、重量级的依赖**上完全正当。  
> 判断标准：这个依赖是否在所有路径上都需要？如果只有少数路径需要，延迟导入能显著降低  
> 启动时间与安装门槛。

### 2.5.3 `vision_service.py` —— 图像预处理 + 三级降级 ⭐

> 手机原图动辄 4~8MB、4000px 宽，直接 base64 塞给本地 7B 模型，光是视觉编码就会拖到几十秒，  
> 而且超出模型的有效感受野。统一压到 1280px 长边、JPEG q=88，体积降一个数量级，视觉信息几乎无损。

#### 预处理：不只是压缩

```python
def prepare_image(self, raw: bytes, mime: str = "image/jpeg") -> tuple[bytes, str, ImageMeta]:
    max_bytes = int(self.settings.max_image_mb * 1024 * 1024)
    if not raw:
        raise ImageValidationError("上传内容为空，请重新选择图片")
    if len(raw) > max_bytes:
        raise ImageValidationError(...)

    try:
        image = Image.open(io.BytesIO(raw))
        image.load()
    except UnidentifiedImageError as exc:
        raise ImageValidationError("无法识别该图片格式，请上传 JPG / PNG / WEBP 格式的图片") from exc
    except Exception as exc:  # 损坏文件、解压炸弹等
        raise ImageValidationError(f"图片解析失败：{exc}") from exc

    warnings: list[str] = []
    if min(original_width, original_height) < _MIN_USABLE_SIDE:
        warnings.append(f"图像分辨率偏低（{original_width}×{original_height}），细节可能不足以支撑判断...")

    # 手机拍摄的图片常带 EXIF 旋转标记，不校正会以错误方向送进模型
    image = ImageOps.exif_transpose(image)
    if image.mode != "RGB":
        image = image.convert("RGB")

    # 亮度评估：过暗/过曝是本地模型误判的高频原因，提前提示用户
    try:
        stat = ImageStat.Stat(image.convert("L"))
        mean_brightness = float(stat.mean[0])
        if mean_brightness < _DARK_THRESHOLD:
            warnings.append("图像整体偏暗，可能遗漏皮损细节，建议在自然光下重拍")
        elif mean_brightness > _BRIGHT_THRESHOLD:
            warnings.append("图像存在过曝，颜色信息可能失真，建议避免直射闪光灯")
    except Exception:
        pass
```

四个值得注意的点：

1. **`image.load()` 显式加载**。PIL 的 `open()` 是惰性的，真正的解码错误要到访问像素时才抛。  
   提前 `load()` 能把"损坏文件"的错误在这里捕获，而不是在后续 `resize` 时莫名其妙地炸。
2. **`ImageOps.exif_transpose`**。手机拍照会写 EXIF Orientation 标记。不校正的话，  
   模型收到的是**躺倒的图片**——皮肤照片的形态描述会全错。这是一个极容易被忽略的坑。
3. **亮度评估 + 主动提示**。过暗/过曝是本地模型误判的高频原因。与其让模型瞎猜，  
   不如在 warnings 里提示用户重拍。**这是"把模型能力的边界告诉用户"的设计**。
4. **`ImageMeta` 随诊断一起返回**，注释说是"便于排查「模型看不准」的锅在谁身上"。  
   这种"让系统可诊断"的意识很值得学。

#### 三级 format 降级

```python
async def _analyze_via_rest(self, image: bytes, user_text: str) -> str:
    """REST 路径：三级 format 降级。"""
    schema = inline_json_schema(VisionDiagnosis.model_json_schema())

    # 依次尝试：Schema 约束 -> 仅 JSON -> 自由文本（提示词已含结构要求）
    strategies: list[tuple[str, dict | str | None]] = [
        ("json_schema", schema),
        ("json", "json"),
        ("freeform", None),
    ]

    last_error: Exception | None = None
    for index, (name, response_format) in enumerate(strategies):
        try:
            content = await self.client.chat(
                self.settings.vision_model, messages,
                images=[image],
                response_format=response_format,
                options=self._build_options(),
                timeout=self.settings.vision_timeout,
            )
        except ModelOutputError as exc:
            # 该模型不支持此 format，换更宽松的策略重试
            logger.warning("视觉分析 format={} 被拒绝：{}，降级重试", name, exc.message)
            last_error = exc
            continue

        if index > 0:
            logger.info("视觉分析使用降级策略：{}", name)
        return content

    raise ModelOutputError(
        "视觉模型拒绝了所有输出格式策略，请检查模型是否支持结构化输出",
        detail=str(last_error),
    )
```

**这是"策略降级链"的教科书式实现**：

| 级别 | `format` 取值 | 保证              | 代价     |
| -- | ----------- | --------------- | ------ |
| 1  | JSON Schema | 语法 + 结构双重约束，最可靠 | 需要模型支持 |
| 2  | `"json"`    | 仅保证合法 JSON      | 字段可能缺  |
| 3  | `None`      | 什么都不保证，靠提示词     | 解析可能失败 |

设计要点：

- **只捕获 `ModelOutputError`**（`ollama_client` 在 HTTP ≥400 时抛的），其他异常  
  （如 `OllamaUnavailableError`）直接向上冒泡——因为没有降级能救"服务没起"。  
  **降级链的粒度必须精确**，捕获过宽会把不可恢复的错误也吞掉。
- **每次降级都记日志**，注释说"便于定位是哪个模型不配合"。换了模型后发现老是降级，日志会告诉你。
- **`last_error` 保留最后一次失败原因**，最终抛错时作为 detail 带上。

#### 为什么视觉不走流式

> **视觉分析不走流式**。诊断结果是一个 JSON 对象，必须拿到完整内容才能校验；  
> 流式吐一半的 JSON 无法解析。真正需要流式体验的是后面的自然语言回答。

**这条判断很关键**：不是"能流式就流式"，而是**看数据的完整性要求**。  
JSON 是不可分割的语义单元，流式反而有害。而自然语言回答天然可分块。

### 2.5.4 `retrieval_service.py` —— 混合检索与 RRF ⭐

这是服务层最复杂也最有技术含量的文件（415 行）。

#### 为什么需要混合检索

> - **向量召回**（Chroma 余弦）解决「语义相似但用词不同」的问题。  
>   用户说「脸上起红疙瘩」，文档里写「面部丘疹性皮损」，只有向量能匹配上。
> - **BM25 关键词召回**解决「专有名词必须精确命中」的问题。  
>   疾病名、药物名、缩写靠语义向量经常召回不准。
> - **RRF** 解决「两路分数不可比」的问题。余弦相似度是 0~1 的有界值，  
>   BM25 分数是无界的 TF-IDF 加权和，直接加权求和需要凭经验调缩放系数；  
>   RRF 只用「排名」不用「分数」，天然规避量纲问题。

#### 中文 BM25 的坑


```python
def _ensure_bm25(self) -> None:

            self._bm25 = None
            self._stamp = 0
            return

        data = vector_store.get_collection().get(include=["documents", "metadatas"])
        ...
        corpus = [tokenize(text or "") for text in docs]

```

**为什么 BM25 需要自己维护索引**：Chroma 只管向量，BM25 是纯内存的。文档变更后必须重建，  
否则关键词召回会拿到已删除的文档。

**用 `count()` 当版本号的巧妙之处**：不需要显式维护"上次更新到哪个版本"，只要数量变了就重建。  
**代价**：如果删一个加一个（数量不变），索引不会失效。这是已知的近似——  
但 `IngestService` 在每次入库/删除后都显式调用 `retrieval_service.invalidate()`（把 `_stamp` 置 -1），  
所以实际上不会漏。

```python
def invalidate(self) -> None:
    """标记索引失效（入库/删除文档后调用）。"""
    with self._lock:
        self._stamp = -1
```

**`_stamp = -1` 而不是 `None`**：因为类型是 `int`，用 -1 保证 `current == self._stamp` 永远为假。  
`IngestService._invalidate_retrieval_index()` 是调用点，且用 try/except 包住  
（"索引失效失败不影响入库结果"）。

**线程安全**：`threading.Lock()` 保护重建过程。因为索引可能被多个请求线程同时读到，  
而重建是非原子操作（多次赋值），加锁避免读到"半新半旧"的状态。

#### RRF 融合

```python
def _rrf(self, rankings: list[tuple[list[str], float]], k: int) -> dict[str, float]:
    """Reciprocal Rank Fusion。

    公式：``score(d) = Σ_r weight_r / (k + rank_r(d))``，rank 从 1 开始。
    k 取 60（原论文经验值），作用是压平头部差异，避免某一路的 top-1
    因为「恰好排第一」而获得过高权重。
    """
    fused: dict[str, float] = {}
    for order, weight in rankings:
        for rank, chunk_id in enumerate(order, start=1):
            fused[chunk_id] = fused.get(chunk_id, 0.0) + weight / (k + rank)
    return fused
```

**RRF 的核心洞察**：不同检索器的分数不可比，但**排名可比**。  
所以只用排名：第 1 名得 `1/(60+1)`，第 2 名得 `1/(60+2)`……多个检索器的得分相加。

`k=60` 的作用：`k` 越大，`1/(k+rank)` 随 rank 的变化越平缓。  
`k=60` 时，第 1 名和第 2 名的差距是 `1/61 - 1/62 ≈ 0.00026`，非常小——  
意味着"某一路排第一"不会带来压倒性优势，**必须两路都排前面才能得高分**。  
这正是 RRF 抗单路噪声的机制。三条测试锁它的数学性质：

```python
test_rrf_favors_documents_ranked_high_in_both_lists  # 两路都高 → 总分高
test_rrf_rewards_consistency_over_single_list_top    # 一致性优于单路拔尖
test_rrf_weights_shift_ranking                       # 权重能改变排序
```

**排序信号与展示信号分离**：

```python
# 展示分：加权混合（余弦相似度 + 归一化 BM25），同尺度、直观
blended: dict[str, float] = {}
for chunk_id in doc_map:
    sim = similarities.get(chunk_id, 0.0)
    kw = keyword_scores.get(chunk_id, 0.0)
    has_vec = chunk_id in similarities
    has_kw = chunk_id in keyword_scores
    if has_vec and has_kw:
        blended[chunk_id] = cfg.vector_weight * sim + cfg.bm25_weight * kw
    elif has_vec:
        blended[chunk_id] = sim
    else:
        blended[chunk_id] = kw * 0.9  # 纯关键词命中略降权

# 排序以 RRF 为准（鲁棒），展示以混合分为准（直观）
ranked_ids = sorted(doc_map, key=lambda cid: rrf_scores.get(cid, 0.0), reverse=True)
ranked_ids = [cid for cid in ranked_ids if blended.get(cid, 0.0) >= cfg.min_relevance]
```

> 关于返回给前端的 `score`：排序用 RRF，展示用加权混合分。  
> **排序信号和展示信号分开是刻意的——前者要的是鲁棒，后者要的是直观。**

> 💡 **学习点**：这是一个高级的工程判断。RRF 分数量级很小（0.01 级别），直接展示给用户  
> 会觉得"相关度怎么这么低"。所以用"加权混合分"展示（0~1 之间，符合直觉），  
> 但排序仍用 RRF（抗噪声）。**把"内部最优"和"对外可解释"解耦**，  
> 这个模式在任何需要给用户展示算法结果的场景都适用。

注意 `min_relevance` 过滤用的是 **blended 分**（不是 RRF 分）——因为 RRF 分太小，没法设阈值。  
而 `kw * 0.9` 体现"两路都命中更可信"。

### 2.5.5 `fusion_service.py` —— 融合的三层职责

"融合"容易被误解成玄学概念，但代码里它非常具体：**三件明确的事**。

| 职责       | 方法                | 输入 → 输出                   |
| -------- | ----------------- | ------------------------- |
| 一、构造检索意图 | `build_queries()` | 视觉结果 + 用户文本 → 1~3 条 query |
| 二、构造上下文  | `build_context()` | 检索结果 → 带编号的文本块            |
| 三、构造生成链  | `build_*_chain()` | LLM → LCEL 链              |

#### 职责一：视觉结果 → 检索意图

这是"融合"的技术落点。确定性兜底版本：


注意三条 query 的设计意图，与提示词 `QUERY_BUILD_PROMPT` 的要求一一对应：

1. 疾病方向（`hypothesis.name`）
2. 形态学特征（部位 + 颜色 + 形态）
3. 鉴别与危险信号处置（**根据 `red_flags` 是否为空走两条不同路径**）

**第三条的分支尤其精妙**：如果视觉发现了危险信号，检索"危险信号就医指征"（帮用户判断严重性）；  
否则检索"护理注意事项"（给出日常建议）。**同一个字段驱动了不同的检索意图**——  
这就是结构化视觉结果的价值。

LLM 版本则在兜底基础上"锦上添花"：


而不是丢弃 LLM 的结果。这是"两者取长"而非"二选一"。

#### 职责二：上下文拼接 + 字符预算

```python
# 注入提示词的参考资料总长度预算（字符）。
# 本地 7B 模型 num_ctx=8192 时，光资料占满会挤掉对话历史与生成空间，
# 因此显式设一个上限，超出的片段直接丢弃（已按相关度排序，丢尾部损失最小）。
CONTEXT_CHAR_BUDGET = 4000

@staticmethod
def build_context(sources: list[RetrievedChunk]) -> str:
    if not sources:
        return "（本次未检索到相关资料，请在回答中明确说明「现有资料未涵盖该问题」）"

    blocks: list[str] = []
    used = 0
    for index, item in enumerate(sources, start=1):
        header = f"[{index}] 《{item.title or item.source}》"
        if item.category:
            header += f"（分类：{item.category}）"
        if item.page:
            header += f" 第 {item.page} 页"
        block = f"{header}\n{item.snippet}"

        if used + len(block) > CONTEXT_CHAR_BUDGET:
            logger.debug("上下文预算用尽，丢弃 {} 条尾部资料", len(sources) - index + 1)
            break
        blocks.append(block)
        used += len(block)

    return "\n\n".join(blocks) if blocks else "（本次未检索到相关资料）"
```

三个细节：

1. **空结果明确告知模型**："本次未检索到相关资料，请在回答中明确说明「现有资料未涵盖该问题」"。  
   这不是给用户看的，是**给模型的指令**。如果传空字符串，模型可能自己脑补；  
   明确写一句话，模型就会说"资料未涵盖"。
2. **编号 `[1]` `[2]` 是脚注锚点**。提示词要求模型写"……（见 \[1\]\[2]）"，  
   前端按同样顺序渲染 `sources`，两边就能对上。**这是"检索结果"和"引用标注"之间的隐式契约，  
   靠约定 + 一致顺序实现。**
3. **超预算就 `break`**（不是 `continue`）。因为片段已按相关度排序，后面的更不重要。

#### 职责三：LCEL 链

```python
@staticmethod
```

`prompt | llm` 是 LangChain 的 LCEL 语法，等价于"先填模板再调模型"。

#### 链的缓存

```python
def _chain(self, kind: str) -> Any:
    """惰性构建并缓存生成链。"""
    if kind not in self._chains:
        llm = get_text_llm()
        builder = {
            "kb_qa": self.fusion_service.build_kb_qa_chain,
```

### 2.5.6 `safety_service.py` —— 不变量 ⭐⭐

**这是全项目最应该逐行读的文件。** 它只有 154 行，但每一处都体现"医疗场景的安全意识"。

#### 为什么不用 LLM 做安全判断

> 模型的安全意识是概率性的——同一张图问十次，可能有八次提示就医、两次轻描淡写。  
> 医疗场景下这种不确定性不可接受。因此本模块用**关键词规则表**做确定性扫描，  
> 与模型自述的 `red_flags` **取并集**，再按严重度取最大值。  
> 规则只会把风险等级**上调**，永远不会下调，保证「宁可保守」。

这段文档还给出了一个可测试性的红利：

> 安全层是**规则驱动**的，所以可以被精确断言——这正是选择规则而非 LLM 的价值。

对比一下：如果安全判断交给 LLM，测试只能写"大概会提示就医"这种模糊断言，  
或者 mock 一个固定输出（那测的就不是真实行为了）。而规则版本可以断言精确值。

#### 严重度映射

```python
_SEVERITY: dict[RiskLevel, int] = {
    RiskLevel.LOW: 0,
    RiskLevel.MEDIUM: 1,
    RiskLevel.HIGH: 2,
    RiskLevel.URGENT: 3,
}
```

**把枚举映射成可比较的整数**，这样"取最大值"和"是否达到 HIGH"都能用数值比较表达。

#### 两级信号源 —— 本项目最精妙的修复 ⭐

`assess()` 的文档用了整整一节解释，**这是全项目最值得学习的一段工程思考**：

> 早期实现把所有文本（用户输入 + 视觉结果 + 生成的答案）拼在一起扫描，  
> 实测会产生明显的**假阳性**：用户只是泛泛地问「色素痣出现哪些变化需要就医」，  
> 而模型的回答本身就在**逐条列举**危险信号（不对称、边界不规则、迅速增大……），  
> 这些词被扫描命中，于是系统给一个纯知识性提问打上了「⚠️ 请尽快就医」横幅。
>
> 因此改为两级：
>
> | 级别  | 信号源            | 作用                               |
> | --- | -------------- | -------------------------------- |
> | 强信号 | 用户输入 + 视觉结构化结果 | 驱动风险升级与强制就医横幅——这是「当事人自身」的证据      |
> | 弱信号 | 生成的答案文本        | 仅补充进 `red_flags` 供用户自查，**不参与升级** |
>
> 这样既保住了「模型淡化用户危险信号时仍会升级」的安全性（因为危险信号在用户输入里），  
> 又消除了「回答提到疾病症状就报警」的噪声。

代码实现：

```python

merged: list[str] = []
for flag in [*model_flags, *case_flags, *answer_flags]:
    cleaned = truncate(str(flag).strip(), 80, suffix="")
```

> 💡 **学习点**：这是"**区分信号与噪声**"的典型案例。表面上看，  
> "从答案里扫危险信号"能提高召回（安全性），代价是假阳性（体验）。  
> 但关键洞察是：**这两种信号的可信度不同**——用户说"我的痣在变大"是事实陈述，  
> 而答案说"痣变大会有风险"是知识陈述。把它们区分开，就能既保安全又消噪声。
>
> **当你发现某个检查规则"既想抓这个又想抓那个"时，先问：这些信号的可信度一样吗？**  
> 如果不一样，就该分层，而不是调阈值。

### 2.5.7 `ingest_service.py` —— 文档管线 ⭐

#### 取舍一：为什么不用 LangChain Community 的 DocumentLoader

> **不用 LangChain Community 的几十种 DocumentLoader**，而是自己写轻量解析。  
> 原因是 community 的 loader 依赖面极广（unstructured、pdfminer、pillow……），  
> 本地部署装起来又慢又容易版本冲突；本项目只需 5 种格式，手写反而更可控。  
> 分块仍然使用 LangChain 的 `RecursiveCharacterTextSplitter`（中文分隔符已适配），  
> 保持「LangChain 架构」的抽象一致性。

**注意这里的分寸感**：不盲目用框架，也不盲目排斥框架。解析（5 种格式，边界清晰）自己写，  
分块（算法复杂，LangChain 做得好）用框架。**判断依据是"这件事的复杂度是否值得一个依赖"。**

自定义解析器用字典分派：

```python
_LOADERS = {
    ".pdf": _load_pdf, ".docx": _load_docx, ".html": _load_html, ".htm": _load_html,
    ".md": _load_markdown, ".markdown": _load_markdown, ".txt": _load_markdown,
}

def load_file(path: Path) -> list[Document]:
    suffix = path.suffix.lower()
    loader = _LOADERS.get(suffix)
    if loader is None:
        raise DocumentParseError(f"不支持的文件格式 {suffix}，当前支持：{', '.join(sorted(SUPPORTED_SUFFIXES))}")
    try:
        return loader(path)
    except DocumentParseError:
        raise
    except Exception as exc:  # 所有其它异常都翻译成业务异常

```

**`except DocumentParseError: raise` 这一句很关键**：先让业务异常原样穿透，再捕获兜底 `Exception`。  
如果不写这句，"解析失败"的错误会被包装成"解析失败：解析失败：…"这种嵌套。  
**这是异常翻译的标准写法**：先放行已知的业务异常，再把未知异常翻译成业务异常。

#### 取舍二：doc_id = 内容 SHA1

```python
@staticmethod
def compute_doc_id(path: Path) -> str:
    """按文件内容计算 doc_id（SHA1 前 16 位）。

    用内容哈希而非 UUID：同一文件重复上传幂等，内容变更即视为新版本。
    """
    digest = hashlib.sha1(path.read_bytes()).hexdigest()
    return digest[:16]
```

配套的"先删后写"：

```python
# 先删后写：保证「重新上传同一文档」得到的是覆盖而非叠加

if removed:
    logger.info("覆盖旧版本 {}，清理 {} 个旧向量块", doc_id, removed)
```

> 💡 **学习点**：**内容寻址（content-addressed）** 是幂等设计的经典手法。  
> 对比 UUID 方案：UUID 每次上传都是新文档，库里会积累 N 份重复内容，  
> 且无法表达"这是同一文档的新版本"。内容哈希天然表达了"相同内容 = 同一文档"，  
> "内容变了 = 新版本"。代价是"只改了一个字也要全量重传"，但对知识库场景完全可接受。  
> **这类"用内容标识替代随机标识"的取舍，在缓存、去重、增量同步里都常见。**

#### 取舍三：Markdown 两级切分

> 把章节路径写进 metadata，再按字符递归切。这样检索时能回答「这个片段属于哪一节」，  
> 对医学文档尤其重要（**同样的句子放在「鉴别诊断」和「护理建议」下含义完全不同**）。


#### 分块与序号

#### 中文清洗的一个隐蔽陷阱 ⭐

```python
# 只匹配「横向」空白（普通空格 / 制表符 / 全角空格），刻意排除换行，
# 以免把段落分隔也当成 PDF 噪声删掉
_CJK_INNER_SPACE = re.compile(r"(?<=[\u4e00-\u9fff])[ \t\u3000]+(?=[\u4e00-\u9fff])")

def clean_text(text: str) -> str:
    text = text.replace("\r\n", "\n").replace("\r", "\n")
    text = _CONTROL_CHARS.sub(" ", text)
    # 修复 PDF 常见的「中文之间被塞了空格」。
    # 这里必须用 [ \t\u3000] 而不是 \s —— \s 包含 \n，
    # 会把汉字之间的换行也一并删掉，导致整篇文档的段落边界全部消失、
    # 分块退化成一大坨连续文本。这个坑很隐蔽，已用测试锁住。
    text = _CJK_INNER_SPACE.sub("", text)
    text = _MULTI_BLANK.sub("\n\n", text)
    return text.strip()
```

**这是全项目最隐蔽的一个坑，值得单独记住。**

- 正则里的 `\s` = `[ \t\n\r\f\v]`，**包含换行**
- 如果写成 `(?<=[\u4e00-\u9fff])\s+(?=[\u4e00-\u9fff])`，那么 `"湿疹\n护理"` 中的 `\n`  
  会被匹配并删除，变成 `"湿疹护理"`
- 后果：**整篇文档的段落边界全部消失**。`RecursiveCharacterTextSplitter` 的首要分隔符是 `"\n\n"`，  
  没有换行就只能按句号切，甚至退化成按字切
- 而且这个 bug **不会报错**，只会让检索质量悄悄变差——这才是它隐蔽的原因

代码用 `[ \t\u3000]`（普通空格、制表符、全角空格）精确表达"横向空白"，  
并用了**前后向断言** `(?<=...)` / `(?=...)` 保证替换时只删中间的空格、不动汉字。

> 💡 **学习点**：**正则里的 `\s` 是最容易出错的元字符之一**，因为它对"空白"的定义比你想象得宽。  
> 写正则时要明确问："我要的是横向空白还是包含换行的空白？"  
> 这个项目用一个测试把结论固定下来，是应对这类坑的正确姿势。

#### 不阻塞事件循环


`run_in_threadpool` 把同步的 CPU 密集操作（PDF 解析、向量化）丢到线程池，

> 💡 **这一点非常重要**：FastAPI 的 `async def` 端点在事件循环里执行。  
> 如果你在里面做了同步阻塞操作（PIL 解码、pdf 解析、`requests` 调用），

>
> 注意 `_ingest_sync` 是同步方法、`ingest_file` 是异步方法——  
> **这个命名与拆分的意图就是把"阻塞部分"隔离出来，方便丢进线程池**。这是可读性上的用心。

### 2.6.2 `nodes.py` —— 七个节点

节点的职责边界表（`nodes.py:9-17`）本身就是最好的文档：

| 节点             | 职责                  | **不做什么**   |
| -------------- | ------------------- | ---------- |
| preprocess     | 输入净化、图片解码与预处理       | 不判意图       |
| route          | 意图分类（规则优先 + LLM 兜底） | 不做检索       |
| vision_analyze | 调 VL 模型产出结构化诊断      | 不生成面向用户的回答 |
| build_query    | 把视觉/文本转成检索意图        | 不执行检索      |
| retrieve       | 混合检索 + 拼上下文         | 不做重排以外的加工  |
| generate       | 调 LLM 产出自然语言回答（流式）  | 不做安全审查     |
| safety_review  | 规则审查 + 答案合规化        | 不改写医学内容    |

**"不做什么"这一列比"做什么"更有价值。** 它明确划定了边界，防止节点膨胀成"什么都干"的上帝函数。  
举两个例子：

- `build_query` 明确"不执行检索" → 所以它能脱离数据库独立测试
- `safety_review` 明确"不改写医学内容" → 所以它只做追加，不做修改，行为可预测

节点的设计说明也很关键：

> 每个节点是一个纯函数式的「状态进、增量出」单元，只依赖注入进来的 service，  
> **不直接碰数据库、不直接碰 HTTP**。这样切分的好处是：单个节点可以脱离整图独立测试，  
> 也便于后续把某一个节点换成更复杂的实现。

#### preprocess：输入净化

```python
def preprocess(self, state: AgentState) -> dict[str, Any]:
    """净化文本输入、解码并预处理图片。

    图片预处理放在这里而不是 API 层，是为了让「base64 直传」与「multipart 上传」
    两条入口共用同一套校验逻辑，也保证流式与非流式响应行为一致。
    """
    started = time.perf_counter()
    question = (state.get("question") or "").strip()
    update: dict[str, Any] = {"question": question, "errors": list(state.get("errors") or [])}

    raw_b64 = state.get("image_bytes")
    if raw_b64:
        try:
            # 兼容「带 data URI 前缀」与「纯 base64」两种写法
            payload = raw_b64
            if isinstance(payload, str) and payload.startswith("data:"):
                payload = payload.split(",", 1)[-1]
            decoded = base64.b64decode(payload, validate=False)
            image_bytes, mime, meta = self.vision_service.prepare_image(
                decoded, state.get("image_mime") or "image/jpeg"
            )
            update.update({"image_bytes": image_bytes, "image_mime": mime, "image_meta": meta.model_dump()})
        except (binascii.Error, ValueError, ImageValidationError) as exc:
            logger.warning("图片预处理失败：{}", exc)
            message = exc.message if isinstance(exc, ImageValidationError) else f"图片解码失败：{exc}"
            update["errors"] = [*update["errors"], message]
            update.update({"image_bytes": None, "image_meta": None})

    update["timings"] = _elapsed(state.get("timings") or {}, "preprocess", started)
    return update
```

**"图片预处理放在节点而不是 API 层"这个决策值得深思**。理由是"两条入口共用校验逻辑"：  
`/agent/chat` 传 base64，`/diagnosis/image` 传 multipart。如果校验逻辑写在 API 层，要写两遍。  
放在节点里，两条入口都经过同一个 `preprocess` 节点。

**兼容 data URI 前缀**：前端可能传 `"data:image/jpeg;base64,xxxx"` 整串，也可能传纯 base64。  
`payload.split(",", 1)[-1]` 一句话兼容两种（没有逗号时返回原串）。  
`test_preprocess_tolerates_data_uri_prefix` 锁这个行为。

**失败不抛异常**：`except` 里把错误**记录到 `state["errors"]` 然后继续**。  
这是"降级"哲学的体现——图片坏了不该让整次对话失败，用户还能得到文本回答。

#### route：规则优先 ⭐

```python
def route(self, state: AgentState) -> dict[str, Any]:

    决策顺序（**规则优先**，因为本地 LLM 调用一次要 1~2 秒，
    而 90% 的情况用关键词就能判准）：
    1. 有图片（且预处理成功）→ 图片诊断；
    2. 命中皮肤关键词 → 知识库问答；
    3. 匹配寒暄模板 → 闲聊；
    4. 其余交给轻量模型分类，失败则回落到知识库问答。
    """
    question = state.get("question") or ""

    if state.get("image_bytes"):
        intent = Intent.IMAGE_DIAGNOSIS.value
    elif not question:
        intent = Intent.CHITCHAT.value
    elif any(keyword in question for keyword in SKIN_KEYWORDS):
        intent = Intent.KB_QA.value
    elif _CHITCHAT_RE.match(question):
        intent = Intent.CHITCHAT.value
    else:
        intent = self._llm_route(question)
    ...
```

**这个 if-elif 链的顺序就是优先级，每一级都有理由**：

1. **图片优先于一切**。测试名直说了理由：`test_image_intent_wins_over_text`  
   的 docstring 是"图片信息量远大于文字"。用户发了图 + 写"这是什么"，显然该走视觉分析。
2. **空文本 → 闲聊**，避免无意义检索。
3. **皮肤关键词 → 知识库问答**。60+ 个关键词覆盖疾病名、形态学词、护理词、口语提问。  
   命中就直接判，省掉一次 1~2 秒的模型调用。
4. **寒暄正则 → 闲聊**：
   ```python
   _CHITCHAT_RE = re.compile(
       r"^\s*("
       r"你好|您好|hi|hello|hey|哈喽|嗨|在吗|在不在|早上好|晚上好|下午好|"
       r"谢谢|感谢|多谢|thanks|thank you|"
       r"你是谁|你叫什么|介绍一下你|你能做什么|你会什么|怎么用"
       r")[\s!！。.~～,，]*$",
       re.IGNORECASE,
   )
   ```
   **用 `^...$` 锚定首尾 + 收尾标点容忍**，避免"你好，我脸上长了个疙瘩"被误判成闲聊——  
   因为那整句不匹配模式。**全串匹配是这里的关键。**
5. **兜底 → LLM 分类**。

兜底分类失败时的回落策略：

```python
@staticmethod
def _llm_route(question: str) -> str:
    """用轻量模型兜底分类，任何异常都回落到知识库问答。"""
    try:
        raw = get_fast_llm().invoke(ROUTER_PROMPT.format(message=question[:300])).content
        if isinstance(raw, list):
            raw = "".join(str(part) for part in raw)
        label = str(raw).strip().lower()
        if "chitchat" in label:
            return Intent.CHITCHAT.value
        if "kb_qa" in label:
            return Intent.KB_QA.value
    except Exception as exc:  # 分类失败不应中断对话
        logger.warning("LLM 意图分类失败，回落到知识库问答：{}", exc)
    return Intent.KB_QA.value
```

**失败回落 kb_qa 而不是 chitchat**：宁可多检索一次（浪费一点算力），  
也不要漏答一个真问题（用户体验损失大）。`test_unknown_question_falls_back_to_kb_qa`  
的 docstring 写的就是"宁可多检索，不要漏答"。

注意 `question[:300]` 截断——分类不需要长文本，截断能省 token。

#### vision_analyze：失败降级


`getattr(exc, "message", None)` —— **对 `AppError` 取友好消息，对其他异常用 `str(exc)` 兜底**。  
鸭子类型的宽容写法，避免 `isinstance` 检查。

**降级的连锁反应**：`vision=None` → 流程仍进 `build_query`（路由阶段已判为 image_diagnosis），  
但 `build_query` 会发现 `vision is None`，于是只用 `user_text` 构造 query，  
最终 `generate` 走 `kb_qa` 链。**整条链自动适配，不需要任何特殊分支**——  
这就是"按数据选链"设计的红利。

#### generate：三选一 + 流式内容提取

```python
if vision:
    chain = self._chain("fusion")
    payload = {
        "vision_json": VisionDiagnosis.model_validate(vision).model_dump_json(exclude_none=True),
        "context": context, "question": question or "请分析这张皮肤照片。", "history": history,
    }
elif state.get("intent") == Intent.CHITCHAT.value:
    chain = self._chain("chitchat")
    payload = {"question": question, "history": history}
else:
    chain = self._chain("kb_qa")
    payload = {"context": context, "question": question, "history": history}

try:
    response = await chain.ainvoke(payload)
    content = response.content
    if isinstance(content, list):  # content block 列表
        content = "".join(
            part if isinstance(part, str) else str(part.get("text", "")) for part in content
        )
    answer = str(content).strip()
except Exception as exc:  # 生成失败给可读的兜底话术
    logger.error("生成回答失败：{}", exc)
    answer = (
        "抱歉，本地模型生成回答时出现异常，请稍后重试。"
        "如果问题较紧急，建议直接前往皮肤科面诊。"
    )
```

注释说明了这个判断顺序的理由：

> 三条生成链的选择依据：**视觉结果是否存在**比意图更本质——  
> 只要拿到了视觉诊断，就必须用融合链（因为要输出「观察→方向→依据→建议」结构）。

**意即：不按"从哪条边来的"选链，而按"手里有什么数据"选链。**  
这样新增输入组合时不需要改这段逻辑。

两个细节：

1. **`isinstance(content, list)` 的兼容处理**。LangChain 的 `AIMessage.content` 有时是字符串，  
   有时是 content block 列表（`[{"type": "text", "text": "..."}]`），取决于模型和版本。  
   **这种"防御性兼容"在 LLM 应用里几乎不可避免**，因为它跨了太多版本和供应商。  
   注意同样的处理在 `runner.py:_extract_text`、`nodes._llm_route`、`fusion_service.build_queries`、  
   `retrieval_service._llm_rerank` 里都出现了——**重复 5 次的代码是一个抽取信号**，  
   可以抽成 `core/parsing.py` 里的一个函数。留作思考题。
2. **兜底话术包含就医建议**。即使生成失败，安全提示也不缺席。  
   **安全责任贯穿所有出口，包括错误路径。**

#### safety_review：为什么放在最后

```python
def safety_review(self, state: AgentState) -> dict[str, Any]:
    """规则化安全审查 + 答案合规化。

    放在生成之后而不是之前：因为审查要同时看「模型说了什么」
    和「用户问了什么」，只有答案落地后才能做完整的危险信号扫描。
    """
    report = self.safety_service.assess(
        vision=VisionDiagnosis.model_validate(vision) if vision else None,
        user_text=state.get("question") or "",
        answer_text=state.get("answer") or "",
    )
    answer = self.safety_service.augment(state.get("answer") or "", report)
    return {"answer": answer, "safety": report.model_dump(mode="json"), "timings": ...}
```

注意 `state.get("vision")` 是 dict（因为 `vision_analyze` 里用了 `model_dump(mode="json")`），  
这里要 `VisionDiagnosis.model_validate(vision)` 转回对象。

> 💡 **学习点**：状态里存 **dict 而不是 Pydantic 对象**，是刻意的。  
> 因为 LangGraph 的状态可能需要序列化，dict 是"最通用、最不会出问题"的载体。  
> 代价是每个使用点都要 validate 一次。**这是"边界用强类型，中间用弱类型"的取舍**——  
> 边界指用户输入和模型输出。

`report.model_dump(mode="json")` 里的 `mode="json"` 也很重要：  
它把 `StrEnum` 序列化成普通字符串、`Path` 序列化成字符串，保证能安全地进 SSE 的 JSON。

#### 条件边函数

```python
@staticmethod
def after_route(state: AgentState) -> str:
    """route 之后的走向。"""
    intent = state.get("intent")
    if intent == Intent.IMAGE_DIAGNOSIS.value:
        return "vision_analyze"
    if intent == Intent.KB_QA.value:
        return "build_query"
    return "generate"

@staticmethod
def after_build_query(state: AgentState) -> str:
    """build_query 之后的走向：关闭知识库或没有可用 query 时直接生成。"""
    if not state.get("use_knowledge", True):
        return "generate"
    if not state.get("queries"):
        return "generate"
    return "retrieve"
```

**为什么写成 staticmethod 而不是普通函数？** 因为它们逻辑上属于节点集合，  
但不需要 `self`（不依赖任何 service）。写成 staticmethod 让"不需要状态"这个事实显式化，  
也让测试可以 `AgentNodes.after_route({...})` 直接调用。

`after_build_query` 的两个跳过检索条件都是**性能优化 + 噪声控制**：  
用户主动关了知识库，或者没有生成出 query。三条测试覆盖（`test_after_build_query_*`）。

### 2.6.3 `graph.py` —— 图装配

```python
def build_graph(nodes: AgentNodes) -> Any:
    graph = StateGraph(AgentState)

    graph.add_node("preprocess", nodes.preprocess)
    graph.add_node("route", nodes.route)
    graph.add_node("vision_analyze", nodes.vision_analyze)
    graph.add_node("build_query", nodes.build_query)
    graph.add_node("retrieve", nodes.retrieve)
    graph.add_node("generate", nodes.generate)
    graph.add_node("safety_review", nodes.safety_review)

    graph.add_edge(START, "preprocess")
    graph.add_edge("preprocess", "route")

    graph.add_conditional_edges(
        "route",
        nodes.after_route,
        {"vision_analyze": "vision_analyze", "build_query": "build_query", "generate": "generate"},
    )

    # 融合的关键一条边：视觉结果 -> 检索意图
    graph.add_edge("vision_analyze", "build_query")

    graph.add_conditional_edges(
        "build_query",
        nodes.after_build_query,
        {"retrieve": "retrieve", "generate": "generate"},
    )

    graph.add_edge("retrieve", "generate")
    graph.add_edge("generate", "safety_review")
    graph.add_edge("safety_review", END)

    return graph.compile()
```

模块文档的四个"关键设计点"是对这段代码最好的注解：

1. 对应那一行 `graph.add_edge("vision_analyze", "build_query")`（**普通边，不是条件边**），  
   注释写着"融合的关键一条边"。**拓扑结构本身承载了业务约束**——  
   不需要在 `vision_analyze` 里写"记得去检索"的注释，图不允许它跳过。
2.
3.
4. **这是"单出口"设计的价值**：如果有多条路径通往 END，就必须在每条路径上都记得做安全审查，  
   迟早会漏一条。收敛到单一出口，安全性由拓扑保证。

**图的编译有开销，所以要缓存**：

### 2.6.4 `runner.py` —— 事件协议收敛 ⭐

这是接口层和 LangGraph 之间的**适配层**（adapter），也是本项目"抽象边界"意识最强的文件。

#### 为什么需要这一层

> LangGraph 的 `astream_events` 吐的是框架内部事件（`on_chain_start`、`on_chat_model_stream`、  
> `on_chain_end`……），节点名、数据形状都与前端无关。如果让 API 层直接处理这些，  
> 会把框架细节泄漏到接口契约里，**将来换编排框架就得重写前端**。

**这句话是"防腐层"（anti-corruption layer）思想的标准表述。** 通过一层适配，  
把"框架的内部表示"转换成"自己的稳定契约"。

对外只暴露 8 种事件：

| 事件        | 触发时机        | 前端动作               |
| --------- | ----------- | ------------------ |
| `meta`    | 请求受理 / 意图确定 | 初始化消息气泡、显示意图       |
| `node`    | 每个节点开始/结束   | 更新「正在做什么」进度        |
| `vision`  | 视觉分析节点完成    | 渲染结构化诊断卡片          |
| `sources` | 检索节点完成      | 渲染参考来源列表           |
| `token`   | 生成节点逐 token | 追加流式文本             |
| `answer`  | 兜底整段答案      | 覆盖文本（token 丢失时的补偿） |
| `done`    | 全流程结束       | 收尾、展示耗时与风险等级       |
| `error`   | 任何阶段异常      | 展示错误态              |

**8 种事件覆盖了前端需要的全部信息**，且不含任何 LangGraph 概念。这就是成功的抽象。

#### 事件翻译的核心循环

```python
async for event in self._iter_graph_events(state):
    kind = event.get("event")
    name = event.get("name", "")

    if kind == "on_chain_start" and name in _NODE_NAMES:
        if name == "generate":
            in_generate = True
        yield {"type": "node", "node": name, "label": NODE_LABELS[name], "status": "running"}
        continue

    if kind == "on_chain_end" and name in _NODE_NAMES:
        if name == "generate":
            in_generate = False
        output = (event.get("data") or {}).get("output")
        if not isinstance(output, dict):
            output = {}
        timings = output.get("timings") or {}
        yield {"type": "node", "node": name, "label": NODE_LABELS[name],
               "status": "done", "elapsed_ms": timings.get(name)}

        if name == "route" and output.get("intent"):
            detected_intent = str(output["intent"])
            yield {"type": "meta", "intent": detected_intent}

        if name == "vision_analyze" and output.get("vision"):
            yield {"type": "vision", "data": output["vision"]}

        if name == "retrieve":
            yield {"type": "sources", "data": output.get("sources") or []}

        if name == "generate" and output.get("answer"):
            final_answer = str(output["answer"])

        if name == "safety_review":
            if output.get("answer"):
                final_answer = str(output["answer"])
            safety = output.get("safety")

        for item in output.get("errors") or []:
            if item not in errors:
                errors.append(str(item))
        continue

    if kind == "on_chat_model_stream" and in_generate:
        text = _extract_text(event.get("data", {}).get("chunk"))
        if text:
            answer_parts.append(text)
            yield {"type": "token", "text": text}
```

三个关键设计：

**① `_NODE_NAMES` 集合过滤**

```python
_NODE_NAMES = set(NODE_LABELS)
```

`on_chain_start` / `on_chain_end` 会对**每一个链**触发（包括内部的 prompt chain、LLM chain），  
不只是我们的 7 个节点。用集合过滤掉无关的。  
**没有这个过滤，前端会收到几十个"节点开始"事件。**

**② `in_generate` 标志位 —— token 归属问题** ⭐

文档专门解释了这一点：

> `on_chat_model_stream` 只告诉我们「有模型在流式输出」，不说是哪个节点。  
> 由于本图是**线性执行**的（没有并行分支），用一个 `in_generate` 标志位  
> 在 generate 节点开始/结束时翻转即可准确归属，**不必解析 run 树**。

`astream_events` 的每个事件都带 `run_id` / `parent_ids`，理论上可以解析 run 树判断  
"这个 token 属于哪个节点的哪次调用"。但那段代码复杂且依赖框架内部结构。

这里用一个更简单的洞察：**图是线性执行的**，所以"generate 节点开始后、结束前的所有模型  
token 都是 generate 的"。两行代码解决复杂问题。

> 💡 **学习点**：这是"**利用领域约束简化通用方案**"的典型。  
> 通用方案（解析 run 树）能处理任意拓扑，但复杂、脆弱；  
> 而我们知道自己的图是线性的，于是可以退化成一个布尔标志。
>
> **但要注意这个简化的前提**：文档明确写了"由于本图是线性执行的（没有并行分支）"。  
> 如果将来 graph 里加了并行分支，这个标志位就会出错。  
> **这是一个"有前提的优化"，前提被写在了注释里** —— 这正是负责任的做法。

**③ 错误累积去重**

```python
for item in output.get("errors") or []:
    if item not in errors:
        errors.append(str(item))
```

因为每个节点都可能返回累积的 `errors`（前面讲过节点会拼接上游错误），  
如果不判断就 append，同一个错误会被记 N 次（N = 经过的节点数）。

#### 版本兼容的签名探测 ⭐

```python
def _iter_graph_events(self, state: dict[str, Any]) -> Any:
    """调用 ``astream_events``，并兼容不同版本的签名差异。

    ``version="v2"`` 这个参数在 langchain-core 的不同大版本间经历过
    从「必须显式传」到「默认且已废弃」的变化。这里先做一次签名探测，
    再决定是否传参——比 try/except 更干净（异常方案会消耗掉第一个事件）。
    """
    if self._supports_version is None:
        try:
            params = inspect.signature(self.graph.astream_events).parameters
            self._supports_version = "version" in params
        except (TypeError, ValueError):
            # 签名不可内省（装饰器/C 实现）时按「不传」处理
            self._supports_version = False
    if self._supports_version:
        return self.graph.astream_events(state, version="v2")
    return self.graph.astream_events(state)
```

注释里的"**异常方案会消耗掉第一个事件**"是很关键的洞察。如果用：

```python
try:
    return self.graph.astream_events(state, version="v2")   # ❌ 错误做法
except TypeError:
    return self.graph.astream_events(state)
```

问题是 `astream_events` 返回的是**异步生成器**，构造它时不会执行任何代码，  
`TypeError` 要等到第一次 `async for` 才抛——那时你已经进入了循环，无法简单地重试。  
**所以必须用签名探测，而不是 try/except。**

> 💡 **这一处非常适合作为"你真正读懂了这个文件"的标志。** 它同时涉及：  
> 生成器的惰性求值、`inspect` 的用法、以及"提前探测 vs 事后捕获"的权衡。  
> 结果还被缓存到 `self._supports_version`（用 `None` 表示"未探测"），避免每次请求都探测。

#### 结束时的兜底

```python
streamed = "".join(answer_parts).strip()
# token 流缺失（例如模型不支持流式）时，用节点产出兜底，保证前端一定有内容
if not streamed and final_answer:
    yield {"type": "answer", "text": final_answer}

yield {
    "type": "done",
    "elapsed_ms": int((time.perf_counter() - started) * 1000),
    "answer": final_answer or streamed,
    "safety": safety,
    "has_image": bool(state.get("image_bytes")),
    "intent": detected_intent or (
        Intent.IMAGE_DIAGNOSIS.value if state.get("image_bytes") else Intent.CHITCHAT.value
    ),
    "errors": errors,
}
```

**双重保障**：`token` 事件（逐字）和 `answer` 事件（整段）。  
如果模型不支持流式，一个 token 都没有，那就用 `answer` 兜底。  
`done` 事件里给出 `final_answer or streamed`——**优先用经过 `safety_review` 处理过的完整答案**  
（`final_answer` 在 `safety_review` 分支被更新过），因为那才是带免责声明的最终版。

> ⚠️ **注意一个行为差异**：流式吐给前端的 `token` 是**未追加免责声明**的原始内容，  
> 而 `done` 事件里的 `answer` 是**已追加**的最终版。前端 `ChatPanel.vue` 只用了 `onToken`  
> 追加文本，`onDone` 时**没有用 `answer` 替换 content**。  
> 意味着流式路径下免责声明可能不会显示在气泡里。这是一个值得实际验证的行为差异  
> （见 4.5 节实验 3）。

#### 异常统一转事件

```python
except Exception as exc:  # 统一转成 error 事件
    logger.exception("智能体执行异常")
    payload = error_payload(exc)
    yield {"type": "error", **payload}
    return
```

`logger.exception` 会自动附带 traceback。异常不向上抛，而是转成 `error` 事件——  
**保证 SSE 流总是正常结束**，前端不会遇到"连接断了但没收到错误"的情况。

### 2.7.2 三入口汇流 ⭐

`chat.py` 的模块文档解释了统一入口的动机：

> 如果为「问答」和「诊断」各写一套编排逻辑，二者会迅速分叉——  
> 诊断需要知识库依据、问答也可能被追问「那照片这样是什么」，维护两套必然出现行为不一致。  
> 统一成一张图后，「什么时候检索、什么时候调视觉模型」由一个地方（route 节点）决定。

```python
@router.post("/agent/chat", summary="智能体统一入口（图文混合，支持 SSE 流式）")

    if not payload.stream:

        return ChatResponse(...)
```


三层异常处理器，对应三类错误：

```python
# ① 业务异常 → 用它自带的 http_status
@app.exception_handler(AppError)
async def handle_app_error(request: Request, exc: AppError) -> JSONResponse:
    logger.warning("业务异常 [{}] {} -> {}", exc.code, request.url.path, exc.message)
    return JSONResponse(status_code=exc.http_status, content=error_payload(exc))

# ② 参数校验失败 → 400，并把首个错误点出来
@app.exception_handler(RequestValidationError)
async def handle_validation_error(request, exc) -> JSONResponse:
    first = exc.errors()[0] if exc.errors() else {}
    location = ".".join(str(part) for part in first.get("loc", []))
    return JSONResponse(
        status_code=400,
        content={
            "code": "validation_error",
            "message": f"请求参数有误：{location} {first.get('msg', '')}".strip(),
            "detail": exc.errors()[:5],
        },
    )

# ③ 兜底 → 500，内部细节只进日志不返前端
@app.exception_handler(Exception)
async def handle_unexpected(request, exc) -> JSONResponse:
    logger.exception("未捕获异常: {} {}", request.method, request.url.path)
    return JSONResponse(
        status_code=500,
        content={"code": "internal_error", "message": "服务器内部错误，请查看后端日志", "detail": None},
    )
```

**注意 ② 和 ③ 的对比**：参数错误**把出错位置告诉用户**（`请求参数有误：query ...`），  
而未知异常**只给通用消息**（"请查看后端日志"），细节只进日志。  
**这是"可操作的信息给用户，敏感的信息给日志"的分寸。**

② 里 `exc.errors()[:5]` 只返回前 5 条，避免校验错误过多时响应体爆炸。

横切关注点用中间件加耗时头：

```python
@app.middleware("http")
async def add_timing_header(request: Request, call_next: Any) -> Any:
    """给每个响应加上服务端耗时头，便于前后端联调定位慢点。"""
    started = time.perf_counter()
    response = await call_next(request)
    elapsed = int((time.perf_counter() - started) * 1000)
    response.headers["X-Elapsed-Ms"] = str(elapsed)
    if elapsed > 5000 and not request.url.path.endswith("/health"):
        logger.warning("慢请求 {} {} 耗时 {}ms", request.method, request.url.path, elapsed)
    return response
```

两个细节：

- **排除 `/health`**：健康检查每 30 秒轮询一次（前端 `App.vue` 的 `setInterval`），  
  如果它慢就告警会产生大量噪声
- **用 `time.perf_counter()`** 而不是 `time.time()`：前者是单调时钟，  
  不受系统时间调整影响。**测耗时永远用 `perf_counter`。**

`CORS` 配置有个值得注意的细节：

#### 静态托管的顺序陷阱 ⭐

```python

#    （Starlette 按注册顺序匹配，挂载 "/" 必须放最后）

def _service_info() -> dict[str, Any]:
    ...

if (web_dir / "index.html").is_file():
    # 根路径被前端占用，服务信息挪到 /service-info。
    # 注意顺序：必须在 mount("/") **之前**注册，否则会被静态挂载吞掉
    # （StaticFiles 会去找名为 service-info 的文件，直接 404）。
    app.add_api_route("/service-info", _service_info, tags=["系统"], summary="服务信息")
    app.mount("/", StaticFiles(directory=str(web_dir), html=True), name="web")
    logger.info("已挂载前端静态资源: {}", web_dir)
else:
    app.add_api_route("/", _service_info, tags=["系统"], summary="服务信息")
```

**这是全项目最容易踩的坑之一**，值得完整理解：

1. **Starlette 的路由是按注册顺序匹配的**，第一个匹配的胜出。
2. `app.mount("/", StaticFiles(...))` 会**接管所有未匹配的路径**。
3. 所以如果先 `mount("/")` 再注册 `/service-info`，访问 `/service-info` 时  
   StaticFiles 会去找名为 `service-info` 的**文件**，找不到就 404。
4. 因此：**API 路由 → 自定义根路由 → 静态挂载，顺序不能变**。

而且这里还有个**双模式兼容**的设计：前端构建产物存在时（`web/index.html` 是文件），  
根路径给前端，服务信息挪到 `/service-info`；不存在时（纯 API 模式），根路径给服务信息。  
注释解释了为什么测试要写成"两选一"的断言而不是写死某一种：

> 这个差异取决于构建产物是否存在，把测试跟构建状态绑死会在「本地跑测试」和「容器里跑测试」时表现不一致。

### 2.8.1 `api/index.js` —— 为什么手写 SSE 解析

浏览器有原生 `EventSource`，但这里用了 `fetch` + `response.body.getReader()` 手写解析。原因：  
**`EventSource` 只支持 GET，不能发 POST body，也不能自定义请求头。**  
而这个接口是 `POST` + JSON body（要传图片 base64），`EventSource` 根本做不到。

手写解析的核心是一个**按 `\n\n` 切分事件块的流式解析器**：

```javascript
const reader = response.body.getReader()
const decoder = new TextDecoder('utf-8')
let buffer = ''
let finished = false

const parseBlock = (block) => {
  const lines = block.split('\n')
  let eventName = ''
  const dataLines = []

  for (const line of lines) {
    if (!line || line.startsWith(':')) continue // 注释行 / 心跳
    const colon = line.indexOf(':')
    const field = colon === -1 ? line : line.slice(0, colon)
    let value = colon === -1 ? '' : line.slice(colon + 1)
    if (value.startsWith(' ')) value = value.slice(1)
    if (field === 'event') eventName = value.trim()
    else if (field === 'data') dataLines.push(value)
  }

  if (!dataLines.length) return
  const raw = dataLines.join('\n')
  ...
}

try {
  while (!finished) {
    const { value, done } = await reader.read()
    if (done) break

    buffer += decoder.decode(value, { stream: true })
    // 统一换行符：跨 chunk 的 \r\n 会被拼成 \n\n，处理时不丢事件
    buffer = buffer.replace(/\r\n/g, '\n').replace(/\r/g, '\n')

    let sep = buffer.indexOf('\n\n')
    while (sep !== -1) {
      const block = buffer.slice(0, sep)
      buffer = buffer.slice(sep + 2)
      if (block.trim()) parseBlock(block)
      if (finished) break
      sep = buffer.indexOf('\n\n')
    }
  }
  // 流结束：冲刷解码器，并处理没有以空行结尾的最后一个事件块
  if (!finished) {
    buffer += decoder.decode()
    buffer = buffer.replace(/\r\n/g, '\n').replace(/\r/g, '\n')
    if (buffer.trim()) {
      parseBlock(buffer)
      buffer = ''
    }
  }
  finish({ done: true })
} ...
```

**这段代码里有三个必须处理的流式解析难题**：

1. **分块边界**：一个 SSE 事件可能跨两个 TCP chunk，也可能一个 chunk 里有 3 个事件。  
   所以必须**累积到 buffer 再按分隔符切**，不能假设"每次 read 就是一个完整事件"。
2. **`decoder.decode(value, {stream: true})` 的 `stream: true`**：多字节字符（中文）可能被切在两个  
   chunk 之间。`stream: true` 让 `TextDecoder` 保留不完整的字节序列，下次拼接。  
   **少了这个参数，中文会出现乱码**。最后还要 `decoder.decode()`（不带参数）冲刷残留字节。
3. **换行符归一化**：SSE 规范用 `\n\n` 分隔事件，但 `\r\n\r\n` 也合法。  
   而且 `\r\n` 可能被切在 chunk 边界上（chunk1 以 `\r` 结尾，chunk2 以 `\n` 开始），  
   拼接后变成 `\r\n`。所以每次拼接后都统一替换成 `\n`——**不处理就会漏事件**。

还有一个细节：心跳行。SSE 服务端会定期发注释行（`: ping`）保活，  
`if (!line || line.startsWith(':')) continue` 跳过它们。后端 `EventSourceResponse(..., ping=15)`  
设的就是 15 秒一次心跳。

> 💡 **学习点**：手写流式解析的这三条（边界累积、多字节流式解码、换行归一）  
> 是"文本流协议"的通用清单。无论解析 SSE、NDJSON 还是自定义行协议，都会遇到。  
> 这个实现（约 120 行）是一份很好的参考。

前端还做了一层**字段容错解析**（`resolveNode` / `resolveDiagnosis` / `resolveSources`），  
容忍后端字段名的不同写法：

```javascript
function resolveSources(data) {
  if (Array.isArray(data)) return data
  if (Array.isArray(data?.sources)) return data.sources
  if (Array.isArray(data?.data)) return data.data
  if (Array.isArray(data?.items)) return data.items
  return []
}
```

这是"**客户端比服务端更宽容**"的策略——版本迭代时后端改了字段名，前端不至于立刻崩掉。

### 2.8.2 `composables/useSessions.js` —— 模块级 ref 而非 Pinia

```javascript
import { ref, computed } from 'vue'

/**
 * 会话状态：模块级 ref（不引入 pinia），App 与 ChatPanel 共享同一份状态。
 * 全部会话（含消息）持久化到 localStorage。
 *
 * 注意：这里刻意不使用深度 watch 自动持久化——流式输出时每个 token 都会触发，
 * 会导致频繁 JSON.stringify。改为在「一轮对话结束」等关键节点显式调用 persist()。
 */
const STORAGE_KEY = 'skin-diagnosis:sessions:v1'

const sessions = ref([])
const currentId = ref(null)
let initialized = false
```

**两个值得学的决策**：

1. **用模块级 `ref` 代替 Pinia**。`ref` 定义在模块作用域（不在函数里），  
   所以所有 `import { useSessions }` 的组件共享同一份状态。  
   **代价是必须由组件手动调用 `init()`**（因为模块加载时可能还没有 localStorage），  
   `App.vue` 里就有 `initSessions()`。收益是省掉一个状态管理库。  
   **判断依据**：状态只有一份（会话列表），没有复杂的派生与模块化需求，不值得引入 Pinia。
2. **不用深度 watch 自动持久化**。注释说得很清楚：  
   **流式输出时每个 token 都会触发 watch，导致频繁 `JSON.stringify`**。  
   改为在关键节点显式 `persist()`。
   > 💡 **这是"性能敏感路径上，隐式魔法要换成显式调用"的典型**。  
   > `watch(sessions, persist, { deep: true })` 看起来优雅，但在高频更新的场景下  
   > 会变成性能灾难。**优雅的抽象和高效的实现有时是冲突的，要能识别出这种冲突。**

`localStorage` 写入用 try/except 静默降级：

```javascript
function persist() {
  try {
    localStorage.setItem(STORAGE_KEY, JSON.stringify(sessions.value))
  } catch (err) {
    // 超出配额或隐私模式：静默降级，不影响本次会话使用
  }
}
```

**隐私模式（Safari 无痕）下 `localStorage` 可能直接抛异常**。捕获后静默降级——  
用户仍然能用，只是刷新后丢失历史。这又是一次"降级"哲学的体现。

读取时做**结构归一化**，防止旧版本数据或损坏数据导致崩溃：

```javascript
function normalizeSession(raw) {
  return {
    id: raw?.id || uid(),
    title: typeof raw?.title === 'string' && raw.title ? raw.title : '新会话',
    createdAt: Number(raw?.createdAt) || Date.now(),
    updatedAt: Number(raw?.updatedAt) || Number(raw?.createdAt) || Date.now(),
    messages: Array.isArray(raw?.messages) ? raw.messages : [],
  }
}
```

**每一个字段都做类型校验 + 兜底**。因为 `localStorage` 里的数据可能来自旧版本代码，  
甚至被用户手动改过。**"从持久化存储读数据"和"从网络读数据"一样，都要当作不可信输入处理。**

存储键带版本号 `'skin-diagnosis:sessions:v1'`——将来数据结构变了，改成 `v2` 就能  
优雅地丢弃旧数据，而不是写迁移代码。

发送流程的核心是**先插入两条占位消息，再让事件去更新它们**：

```javascript
session.messages.push({

  image: currentImage?.dataUrl || '', createdAt: Date.now(),
})
maybeRenameFromMessage(session, messageText || '图片咨询')

session.messages.push({
  id: uid(), role: 'assistant', content: '',
  nodeLabel: '', nodeText: '', diagnosis: null, sources: [],
  status: 'loading', error: '', createdAt: Date.now(),
})
// 取回响应式代理，直接修改原始对象不会触发视图更新
const reply = session.messages[session.messages.length - 1]
```

**注意那行注释**："取回响应式代理，直接修改原始对象不会触发视图更新"。  
`session.messages` 是 Vue 的响应式数组，`push` 进去的对象会被代理包装。  
如果保存了 `push` 之前构造的原始对象引用去修改，**Vue 检测不到变化**。  
所以要从数组里取回代理对象。

> 💡 **这是 Vue 响应式的经典陷阱**，注释把它显式记录下来了——  
> 这正是"好注释解释为什么，而不是做什么"的例子。

事件回调直接修改 `reply` 的字段：

```javascript
onNode: (data) => {
  const key = resolveNode(data)
  if (!key) return
  const meta = NODES[key] || { label: key, active: `正在${key}…` }
  reply.nodeLabel = meta.label
  reply.nodeText = meta.active
  scheduleScroll()
},
onVision: (data) => {
  const diagnosis = resolveDiagnosis(data)
  if (diagnosis) reply.diagnosis = diagnosis
  scheduleScroll()
},
onSources: (data) => {
  const list = resolveSources(data)
  if (list.length) reply.sources = list
  scheduleScroll()
},
onToken: (text) => {
  reply.content += text
  scheduleScroll()
},
onDone: () => finish('done'),
onError: (err) => {
  reply.error = err?.message || '生成失败，请重试'
  finish('error')
},
```

**所有状态都存在消息对象里，组件本身不持有"当前生成状态"**。这样切会话、开多个消息都不冲突。

滚动用 `requestAnimationFrame` 节流：

```javascript
function scheduleScroll() {
  if (scrollScheduled) return
  scrollScheduled = true
  requestAnimationFrame(() => {
    scrollScheduled = false
    scrollToBottom()
  })
}
```

**流式输出时 token 到达频率极高（每秒几十个）**，每次都 `scrollTop = scrollHeight` 会导致  
布局抖动。用 rAF 节流保证**每帧最多滚动一次**。

终止逻辑用 `AbortController`：

```javascript
function stop() {
  if (!generating.value) return
  stopped = true
  if (abortController) abortController.abort()
}

// 切换会话时中断仍在进行的生成
watch(currentId, () => {
  if (generating.value) stop()
})

onBeforeUnmount(() => {
  if (abortController) abortController.abort()
})
```

**三种情况都要 abort**：用户点"停止生成"、用户切换会话、组件卸载。  
**漏掉任何一条都会导致"幽灵请求"继续跑并写入已切走的会话。**

`finish` 函数用状态守卫防重复：

```javascript
const finish = (status) => {
  if (reply.status !== 'loading') return    // ← 幂等守卫
  reply.status = stopped ? 'stopped' : status
  generating.value = false
  abortController = null
  touchSession(session)
}
```

因为 `onDone` / `onError` / `finally` 都可能调 `finish`，用 `loading` 状态做守卫保证只生效一次。  
**这又是幂等设计**——和 `SafetyService.augment` 的思路一致。

### 2.8.4 `utils/markdown.js` —— XSS 防护

模型输出要渲染成 HTML，这是经典的 XSS 风险点：

```javascript
// html: false —— 禁止渲染原始 HTML，避免模型输出里携带的标签造成 XSS。
// breaks: true —— 单个换行也换行，更贴近模型输出的自然段。
const md = new MarkdownIt({
  html: false,
  linkify: true,
  breaks: true,
  underline: false,
})

// 外链统一新窗口打开并加 rel，避免覆盖当前页面
md.renderer.rules.link_open = function (tokens, idx, options, env, self) {
  const token = tokens[idx]
  const hrefIndex = token.attrIndex('href')
  if (hrefIndex >= 0) {
    token.attrSet('target', '_blank')
    token.attrSet('rel', 'noopener noreferrer')
  }
  return defaultLinkOpen(tokens, idx, options, env, self)
}
```

三道防护：

1. **`html: false`** —— 最关键的一道。MarkdownIt 默认会透传原始 HTML 标签，  
   而模型输出可能包含 `<script>` 或 `<img onerror=...>`。关掉它只渲染 Markdown 语法。
2. **`target="_blank"` + `rel="noopener noreferrer"`** —— 防止 tabnabbing 攻击  
   （新页面通过 `window.opener` 操纵原页面）。
3. **渲染失败降级为纯文本**：
   ```javascript
   export function renderMarkdown(text) {
     if (!text) return ''
     try {
       return md.render(String(text))
     } catch (err) {
       // 渲染失败时退化为纯文本，保证消息不丢失
       return escapeHtml(String(text))
     }
   }
   ```
   还有 `escapeHtml` 兜底。**再一次是降级哲学：宁可显示转义后的原文，也不要空白。**

> 💡 **学习点**：**任何把 LLM 输出渲染成 HTML 的地方都必须考虑 XSS。**  
> 模型可能被提示注入（用户说"请把这段 HTML 原样输出"），也可能自己产出意外标签。  
> `html: false` 是最省心的防线——功能上只损失"渲染原始 HTML"，  
> 而 RAG 回答本来也不需要这个能力。

## 4.2 十个难点（提前知道能省很多时间）

### 难点 1：LangGraph 的"增量状态"语义

节点返回的是**增量 dict**，不是完整 state。理解这一点才能正确写节点：

```python
# ✅ 正确：累积 errors
errors = list(state.get("errors") or [])
return {"vision": None, "errors": [*errors, message]}

# ❌ 错误：覆盖掉上游错误
return {"vision": None, "errors": [message]}
```

### 难点 2：`astream_events` 的事件类型

`on_chain_start` / `on_chain_end` 会对**每个链**触发。必须用 `_NODE_NAMES` 过滤，  
否则你会看到几十个莫名其妙的"节点开始"。

### 难点 3：token 归属靠布尔标志

`runner.py` 的 `in_generate` 是**依赖"图是线性执行"这个前提**的优化。  
如果你给图加了并行分支，这个标志会失效。

### 难点 4：RRF 为什么不能直接用分数加权

余弦相似度 0~1 有界，BM25 无界。加权求和需要"凭经验调缩放系数"，  
而且换一个 embedding 模型后系数就失效了。RRF 只用排名，**跨模型稳定**。

### 难点 5：Chroma 集合的距离度量不可改

`collection_metadata={"hnsw:space": "cosine"}` **只在首次创建时生效**。  
改配置不重建议直接报维度/度量不匹配错误。所以 `reindex` 里先 `reset_collection()`。

同理，**换 embedding 模型必须 reindex**——向量维度变了。

### 难点 6：`_load_history` 的 `rows[:-1]`

因为 API 层是**先 `add_message` 再读历史**，最后一条是本轮消息。`rows[:-1]` 排除它。  
（docstring 描述的是旧行为，以代码为准。）

### 难点 7：`\s` 包含换行

`ingest_service` 的 `_CJK_INNER_SPACE` 必须用 `[ \t\u3000]` 而不是 `\s`。  
用 `\s` 会删掉汉字之间的换行，**段落边界全消失，检索质量悄悄恶化且不报错**。  
（对应测试：`test_clean_text_removes_intra_cjk_spaces`）

### 难点 8：图片必须先 `exif_transpose`

不校正 EXIF 方向，模型收到的是躺倒的图。这个 bug 的表现是"模型描述得驴唇不对马嘴"，  
而不是报错，所以很难定位。

### 难点 9：`EventSource` 不能发 POST

前端必须用 `fetch` + `getReader()` 手写 SSE 解析。  
手写时三个坑：chunk 边界累积、`stream: true` 解码、`\r\n` 归一。

### 难点 10：pydantic 的解析顺序

**类型解码 → validator**。要拦截解码必须用 `NoDecode`；  
`mode="before"` 只保证在**校验**之前。

## 4.3 陷阱清单（含本次实测发现的问题）

### 🔴 P1：前端上传文档时 `category` 被静默忽略（实测确认）

**现象**：在知识库管理面板选好分类上传文档，入库后分类始终是"其他"。

**根因**：前后端对 `category` 的传递方式约定不一致。

- 前端 `frontend/src/api/index.js`：
  ```javascript
  /**
   * 上传文档：POST /api/v1/kb/documents
   * multipart 字段名 file；分类通过查询参数 category 传递。   ← 注释这样写
   */
  export function uploadDocument(file, category) {
    const form = new FormData()
    form.append('file', file)
    return request(
      http.post('/kb/documents', form, {
        params: { category },                    // ← 走 URL query string
        headers: { 'Content-Type': 'multipart/form-data' },
        timeout: 120000,
      })
    )
  }
  ```
- 后端 `backend/app/api/v1/knowledge.py`：
  ```python
  async def upload_document(
      file: Annotated[UploadFile, File(...)],
      category: Annotated[str, Form(description="文档分类")] = "其他",   # ← 从 multipart body 读
      ...
  ```

`Form(...)` 只从 **multipart body** 取值，`params` 是 **URL query string**，  
两者不通。因此 FastAPI 拿不到 `category`，用了默认值 `"其他"`。

**实测证据**（用 `TestClient` 对同一份文档分别用两种方式上传）：

```
[A] query 参数  -> 200 其他        ← 前端当前的方式，分类被丢弃
[B] form 字段   -> 200 护理建议     ← 后端期望的方式，正常
[C] 入库列表    -> [('probe_a.md', '护理建议')]
```

**影响**：`category` 是检索期的元数据过滤器  
（`retrieval_service._vector_search` 的 `where = {"category": category}`）。  
分类错了，按分类过滤检索会返回空结果；前端列表显示的分组也失真。

**修复方案**（二选一，推荐前者）：

```javascript
// 方案 A：把 category 放进 FormData（与后端 Form 契约对齐）
export function uploadDocument(file, category) {
  const form = new FormData()
  form.append('file', file)
  if (category) form.append('category', category)
  return request(
    http.post('/kb/documents', form, {
      headers: { 'Content-Type': 'multipart/form-data' },
      timeout: 120000,
    })
  )
}
```

```python
# 方案 B：后端改成同时接受 query 参数（不推荐，会让契约更模糊）
category: Annotated[str, Query(description="文档分类")] = "其他",
```

**顺带修复两处不一致**：

1. `api/index.js` 里"分类通过查询参数 category 传递"的注释是错的，要改。
2. `KnowledgePanel.vue:73` 调用 `uploadDocument(pendingFile.value, category.value)`，  
   用户选的值确实传进来了，问题只在这一层之后。

**建议补回归测试**：在后端 `tests/test_api.py` 加一条  
"用 multipart 表单字段传 category，断言返回的 category 与传入一致"，  
把契约锁住。

### 🟡 P2：`_load_history` 的 docstring 与代码不一致

`chat.py:_load_history` 的 docstring 说"这里保留不影响（模型会看到重复…若要严格去重可在拼  
history 时排除最后一条）"，但代码实际已经用 `rows[:-1]` 排除了。  
**docstring 描述的是旧行为**，会误导读者以为存在重复注入。

建议更新 docstring 为："已排除最后一条（本轮用户消息），避免与提示词中的 `{question}` 重复"。

### 🟡 P3：`db.upsert_document` 不更新 `source`

`ON CONFLICT(doc_id) DO UPDATE SET` 里没有 `source` 字段（实测确认：文件名为 `probe_b.md`  
的第二次上传后，列表里显示的仍是 `probe_a.md`）。  
正常流程下无影响（同内容必然同名），但如果通过改名后重传，列表显示的是旧文件名。  
如需修正，把 `source=excluded.source` 加进 `DO UPDATE SET` 即可。

`git status` 显示 4 个未跟踪文件，都会被误提交：

| 文件                          | 来源                                           | 建议                     |

### 🟢 P5：`error_payload` 会把内部异常细节透传给前端

```python
def error_payload(exc: BaseException) -> dict[str, Any]:
    if isinstance(exc, AppError):
        return {"code": exc.code, "message": exc.message, "detail": exc.detail}
    return {"code": "internal_error", "message": f"服务器内部错误：{exc}", "detail": None}
```

非业务异常的 `str(exc)` 被拼进 `message`，而 `runner.py` 会把它作为 SSE `error` 事件  
透传给浏览器。开发期这很方便（能直接看到原因），**公网部署前应改为按 `settings.debug` 决定  
是否带上细节**——README 里也自我提示了"当前尚未做鉴权与限流"。

### 🟢 P6：流式路径下的免责声明可能不显示

`runner` 的 `done` 事件带的是 `safety_review` **处理后**的完整答案（含免责声明），  
但前端 `ChatPanel.vue` 的 `onDone` **没有用这个 answer 覆盖 `reply.content`**——  
它只靠 `onToken` 逐字追加。而 `token` 事件来自 `generate` 节点，**不含追加的免责声明**。

**理论上**：免责声明与紧急横幅可能不出现在流式气泡里（非流式接口 `/diagnosis/image`  
会正常返回）。**这是一个需要实际验证的行为差异**（见 4.5 实验 3）。  
若确认，修法很简单：在 `onDone` 里用 `data.answer` 覆盖 content。

## 结语

这份代码最值得学的不是某个具体技巧，而是**一种习惯**：

> 每写一段代码，都问一句"如果这里出错了，用户会看到什么？"
>
> 于是有了六处降级路径、三级 format 降级、逐字段回退、双重 token 兜底。
>
> 每定一条规则，都问一句"这条规则会被绕过吗？"
>
> 于是有了单出口拓扑、class 属性携带 http_status、代码幂等追加免责声明、  
> 8 条测试锁住安全不变量。
>
> 每做一个取舍，都把理由写进 docstring。
>
> 于是有了这份指南里引用的所有"为什么"。

建议你现在做三件事：

1. **跑一遍阶段一的命令**，把系统在本地跑起来（不需要 Ollama 也能验证工程链路）。
2. **挑一个 4.5 节的实验动手做**，尤其是实验 6（亲手制造一次回归）。
